# Development

- On the embedded (WASM) runtime the `exec` description defers every `mcp__*` nested tool by default (left out of its sections and named on one "Deferred nested tools" line; full description in `ALL_TOOLS`, schema in `toolSchema(name)`) and briefs `send_agent_message`, `list_agents`, `close_agent` and `interrupt_agent` unless the host passes its own `brief_code_tools`, and its compact preamble says cells run in QuickJS, not Node, and that `WebAssembly` exports are async. Georgios asked on 2026-10-25 that nanocode-ts and its demos send only this SDK's native prompts and tool text, so these moved here from host-supplied lists and instructions; with every host instruction removed, a local GLM-5.3 sweep through the Cloudflare demo Worker passed 12 of 12.
- The embedded (WASM) runtime's `exec` description uses a compact preamble (`EXEC_DESCRIPTION_COMPACT`) and compact shared MCP types (`ImageContent`, `ContentBlock`, `CallToolResult` only), keeping every rule: `tools` naming and argument shapes, raw source rather than JSON or fences, the `// @exec:` pragma, awaiting promises, and each global helper. Native runtimes keep the full text (`exec_spec(.., compact: false)`). On 2026-10-25 this took 773 o200k tokens off every request of gakonst/nanocode-ts's Cloudflare demo (Claude-shaped 7,576 to 6,803, Codex 8,304 to 7,531), and a local GLM-5.3 sweep of 12 prompts, 5 with subagents, passed 12 of 12 with no failed tool calls.
- `ToolsBuilder::brief_code_tools(names)` (and `Tools::brief_code_tools`) leaves the listed nested tools out of the `exec` description's full sections on the embedded (WASM) runtime and lists each as one line under "Additional runtime-provided nested tools": its first sentence and argument names, with `ALL_TOOLS` (full description) and `toolSchema(name)` (input schema) for the rest. The tools stay callable. gakonst/nanocode-ts briefs `send_agent_message`, `list_agents`, `close_agent` and `interrupt_agent` on Cloudflare (-432 o200k tokens per request, 2026-10-25). Do not brief `spawn_agent`: in a local GLM-5.3 sweep on 2026-10-25, with its TypeScript declaration gone the model guessed `output_contract` as a string or as JSON Schema `properties` and needed 8 to 15 model calls and up to 12 failed tool calls per subagent turn, against 3 to 8 calls with it.
- In Code Mode cells, `tools.mcp__<server>__<tool>` for a tool that is not in the catalog calls `tools.mcp__<server>__call_tool({ name: <tool>, arguments: input })` when that server exposes one (`code-tools.mjs`), instead of rejecting with `TOOL_NOT_AVAILABLE`. Hosts that defer MCP tools behind `call_tool`, such as gakonst/nanocode-ts's `deferMcp`, name every deferred tool in its description, and models call those names directly: on 2026-10-24 Luna created a gateway sandbox and called `tools.mcp__gateway__compute_terminate`, which failed and left the sandbox running out its paid lease. With this the host can list only `describe_tools` and `call_tool` per server.
- `ChatGateway` (custom models such as GLM-5.3 on Workers AI and OpenRouter, over Chat Completions) folds a second output for a call it already answered into that call's `tool` message instead of rejecting the request with `invalid_history`: Codex logs a Code Mode cell's `notify()` texts as extra `custom_tool_call_output` items with the cell's `call_id` after its output, and Chat Completions takes one tool message per call. On the Cloudflare demo on 2026-10-25 every GLM-5.3 turn whose cell called `notify()` failed at its next model request with "tool output has no matching call in full history". Workers AI requests also carry `x-session-affinity` set to the request's `prompt_cache_key`, which Cloudflare uses to route requests to a replica that holds the prefix in its cache: on 2026-10-25, six repeats of a 7,857-token GLM-5.3 prompt through AI Gateway hit the cache 6 of 6 times with the header and 4 of 10 without, and a cached call cost 191 neurons instead of 1,000. A 36-turn sweep of the demo before this cached 65% of GLM-5.3 input against 98-99% for Claude and Codex.
- The Claude runtime sets `code_only` on WASM whenever the session has a Code Mode host (in-host cells or placed hands), as native runtimes always do. Before, WASM Claude agents ran Code Mode catalogs (`exec` and `wait`) without `code_only`, so a durable cursor saved with direct tools, such as a background child journaled on 2026-10-19 by SDK b651367 and resumed by a Code Mode host, kept offering `submit_result` and the other direct tools while no direct handler was registered: every call answered "Tool is not available in the admitted catalog" and the child failed with "subagent turn ended without a valid submit_result call". Now the cursor upgrades to Code Mode on recovery with its notice, and nanocode-cloudflare-durable's measure-faults legacy scenario completes the child (2026-10-25, 1,433 checks on two seeds). Codex already resumed it.
- `InboxHost::live_deltas()` (default false) lets a host take streamed deltas out of the session log. `TurnInbox`'s sink then publishes root `assistant.delta` and `tool.input.delta` events through `InboxHost::publish_live` as `LoggedEvent`s with `seq` 0, each with `offset`, the UTF-16 length of the item's text before it, and does not append them: `assistant.message` and `tool.call` carry the full text and arguments, so the log keeps those. A run that ends, fails, errors, is steered or whose model call or attempt fails first appends each item's unfinished text as one merged delta with its `offset`, so no text is lost. Reasoning summaries and subagent events are logged as before. Each 100 ms coalesce window of a streamed item was a log row: on 2026-10-25, with 20 chunks 50 ms apart per model call, a turn of 3 Code Mode cells and a reply wrote 89.7 rows (Claude) and 95.3 (Codex) through gakonst/nanocode-ts, and 49.7 and 52.7 with live deltas.
- `Hand::activity()` returns a cloneable `HandActivity` for a host process that must drain before replacing its own binary: `busy()` is true while the hand has a cell running or yielded, a callback awaiting its result, a request in flight, or a result the brain has not acknowledged (retained for resume), `idle()` resolves once none is left, and `drain()` makes the hand refuse every new `Execute` and `Call` with the reply the brain reads as never dispatched (`NOT_RECEIVED`, so the brain's call is unsent and can be retried elsewhere) while `Wait`s for cells it already admitted, cancels and turn bookkeeping still run, so yielded cells can finish. A listening hand counts all its connections; a hand whose brain never returns for unacknowledged results stays busy, so hosts bound `idle()` with a timeout.
- `Hand::header(name, value)` adds an HTTP header to the WebSocket upgrade request of every dial of a `Hand::connect`ed hand, redials included, next to the bearer token; repeating a name sends each value. A name or value that is not a valid HTTP header, or a name the upgrade or credential owns (`Authorization`, `Host`, `Connection`, `Upgrade`, `Sec-WebSocket-*`), fails `Hand::run` before it dials, as an error and not a panic, and listening hands ignore them. Hosts such as Pact announce their build, protocol generations and capabilities on every dial this way while the socket's first frame stays the catalog. A brain that serves none of the hand's protocols answers the upgrade with 426, which ends the hand with `HandEvent::Rejected { status: 426 }` like a refused credential instead of redialing, so the host updates itself rather than looping.
- `RemoteTransport::recover(context)` lets a durable host finish a remote operation that was in flight when its process restarted, instead of reporting an unknown outcome. A tool call whose durable step began but never completed is admitted as interrupted; Claude and Codex now try to recover it before finalizing it. `exec` and `wait` go to `ToolRuntime::recover_code` and `CodeModeHost::recover`, which answers `Ok(None)` unless a host overrides it, so `LocalCells`, local Code Mode and every other host never run anything. Any other tool goes to the `ToolRecovery` a host sets with `ToolsBuilder::tool_recovery`: `recover(name, context)` returns the call's output or `None`. `RemoteCodeModeHost::recover` (cells) and `RemoteCodeModeHost::recover_call` (a hand tool's `RemoteOperation::Call`, decoded as `call` decodes its reply) build the `RemoteContext` from the call's own `ToolContext`, with the same `session_id`, `turn_id` and `call_id` as the dispatch (for Codex the Responses `call_id` and a turn ID of the form `<session>:<n>`, for Claude the `tool_use` ID and the request ID), and call `RemoteTransport::recover`, whose default is `None`. A transport that keeps a table of dispatched operations, such as Pact's Durable Object beside `RemoteClient::resuming`, returns `Some(future)` resolving to the stored `Reply` result for that key, in the form `ResumedReply` yields (`Ok(None)` when it has none); a host's `ToolRecovery` for its hand tools (Bash, Read, Edit, Write, TaskOutput, TaskStop, `exec_command`, `write_stdin`, `apply_patch`) passes the context to `recover_call`. The result is journaled like any completed call. Recovery never dispatches: it reaches only `recover`, `recover_call` and the host's `ToolRecovery`, never `request`, `call` or a tool's own handler. `None`, `Ok(None)`, an error, a cancelled turn or a reply that does not decode finalize the call as before (`Tool execution interrupted by a host crash; outcome unknown`, status `unknown`, `outcome_unknown` true), and tool hooks do not run for a recovered call. Native Claude runtimes offer only `exec` and `wait` at the top level (`code_only`), so `ToolRecovery` is reached natively by Codex with a direct host and on WASM by both backends. Callbacks into the brain's host tools from a cell that is still running are not restored: `RemoteClient` registers a cell's callbacks only when it dispatches, and the recovered reply's nested calls are published as results, not replayed. Hosts need it because a Durable Object can reset while its hand keeps running and already holds the real result.
- A hand holds the callbacks it awaits from its brain across a reconnect of the same runtime instead of failing them when the socket drops. Each pending `Frame::Callback` keeps its id, origin and reply channel, and when the redialed brain sends `Resume` the hand sends every held callback again as the identical frame, so its id, name, input and context (the brain's authorization of the origin) are unchanged and a brain that already ran it before the drop can deduplicate by callback id; a `CallbackResult` for a held id reaches the waiting cell as usual. Callbacks a cell makes while disconnected are held too. A callback that no `Resume` reaches within `ExecutorOptions::callback_hold` (`Hand::callback_hold(duration)`, 60 s by default) fails with the dropped-connection error as before, and a hand that is not resumable or is reset (a new runtime) fails them at once. `DetachedUpdate` and `DetachedComplete` frames for yielded cells used to be discarded while disconnected; the hand now keeps up to 1,024 of them (the oldest dropped first) and sends them in order after the `Resume`, before any later frame.
- Hosts that serve a hand's socket with `serve_queue` or route a call into a shared provider session get small accessors instead of their own adapters: `RemoteCatalog::publishes(name)` says whether a catalog publishes a tool, `RemoteCatalog::frame_limit(limit)` is the hand's `max_frame_bytes` capped at the host's own limit (the largest frame either side writes), `Settlement::outcome()` is the receipt a `CommandQueue` stores for a settlement in the attachment protocol's outcome form (`{"status":"completed","output":…}` or `{"status":"unavailable","message":…}`; none for `Requeue` and `Unknown`), and `ToolContext::with_session_id(id)` is the same call's context under another session ID, as tempoxyz/pyramid's Hand sends every `computer` step to one nanocode-cua session.
- `nanocode_code_mode::remote::MessageLink::new(stream, sink, max_frame_bytes, resumes)` is a `RemoteLink` over a message connection, such as a server's WebSocket, for hosts that accept a hand's socket themselves and serve it with `serve_queue` or a `RemoteClient`: `stream` yields the peer's text messages (an error fails the link with its text; its end is `PEER_CLOSED`), `sink` is shared behind a `tokio::sync::Mutex` with the host's own writes, such as pings, and takes each frame as any `M: From<String>`, and `close` writes nothing, so the host closes with a reason of its own. tempoxyz/pyramid's broker maps axum's `Message` into it instead of implementing the link. `nanocode_chatgpt_extension::Connection::relay(socket, idle, title)` serves browser steps for a host process on a Unix socket of newline-delimited JSON (`hello`, then `call` answered by `result`, and `turn_ended`), naming a session's tab group after the step input field `title`, ending turns idle for `idle`, reconnecting while the connection is live and then waiting for the browser as `finish`; Pyramid's Hand used to carry this loop itself. `remote::websocket(stream, sink, max_frame_bytes, resumes, classify, ping, (interval, timeout))` (native) builds one over a WebSocket library's own messages, which `classify` maps to `SocketMessage`: it answers pings with the pong `classify` gives, fails on a read error or another message and ends on close, and returns a heartbeat future that writes `ping()` every `interval` and resolves with `heartbeat lost` after `timeout` without a pong or `socket write failed`, for `serve_queue`'s `failed`; Pyramid's broker passes axum's `Message` through it instead of tracking pongs itself.
- `nanocode_code_mode::remote::read_catalog(first, timeout, max_frame_bytes)` reads a hand's catalog from the first frame of a socket a host accepted itself (`first` resolves to `None` when the connection ended or failed first, `Some(None)` for a frame that is not text, `Some(Some(text))` otherwise) and fails with `CatalogError::NoCatalog` (none within `timeout`: transient, the hand should reconnect), `Outdated` (not text, or JSON without `definitions`, as `RunnerPool` tells protocols apart) or `Invalid` (a catalog that does not decode). `admit_runtime(previous, connected_before, live, advertised)` is the pure decision whether the runtime a catalog advertises takes the hand: `Fence` for a retired runtime (another runtime took the hand after it), even while its successor's socket is open; `Wait` while another runtime's socket still counts as open, since a host can't tell a live competitor from a dead or sleeping process's socket, so the new runtime reconnects rather than stopping for good; `Retry` for the same runtime while its previous socket on this host is still open; else `Take { replaces }`, where `replaces` retires the previous runtime and forgets its undelivered operations. tempoxyz/pyramid's broker keeps its storage, logging and close codes around both.
- `RemoteContext::new(session_id, call_id, turn_id)` is the context of a call a host queued without a model session, such as a row of tempoxyz/pyramid's `hand_commands` served with `serve_queue`: no model, history, instruction revision or host context, and an output token budget of JavaScript's largest safe integer, the attachment protocol's "no budget beyond the tool's own".
- Streamable HTTP MCP runs on both targets. `streamable_http::spawn_with_sender(url, sender, headers, auth, outgoing, inbound)` drives the same protocol code as the native reqwest `spawn` (session and protocol-version headers, JSON and SSE replies, SSE resumption, 404 re-initialization, bearer tokens and the `BearerSource` 401 retry) over any `nanocode_http::layer::Sender`, with `nanocode_platform::{spawn_local, sleep, timeout}` for its background work on WASM. On WASM `nanocode::tools::mcp` is `nanocode_mcp_tools` for HTTP servers only: `McpBuilder::http_sender` supplies the sender, and stdio servers, OAuth, reloads and the deferred tool-search provider stay native. `PreparedMcpTool` implements `Tool`, so a host awaits `Mcp::prepared_servers` and registers each tool with `ToolsBuilder::tool` on either target, with the catalog's names, schemas and result conversion; gakonst/nanocode-ts does so for its `mcp_servers`.
- MCP transport failures are typed: `nanocode_mcp::Error::Transport` carries a `TransportError` whose `is_unsent()` says the request certainly never reached the server (a connect or request-builder error, a body or parameters that failed to encode, an OAuth or `BearerSource` token that could not be obtained, or a request made after its session closed, such as once a stdio server exited, which `Session` refuses before queueing it), and whose `status()` is the HTTP status of a non-2xx response that failed it: a 4xx without a JSON-RPC error body (401 and 403 challenges included, and 404 when an expired session could not be reopened, so the request was not resent) or any 5xx, whose JSON-RPC error body, if any, stays in the message because a server that failed may have acted. A 4xx JSON-RPC error, such as a 402 payment request, still arrives as `Error::Rpc`, with the reply's status in `RpcError::status`; one sent with a 2xx or over SSE has none. Anything else, such as a stream that broke after a 2xx, has neither and its outcome is unknown, as has `Error::Closed`, which now means the session closed after the request was queued; a request refused by a closed session used to be `Error::Closed` too. `message()` and `Display` keep the earlier text. Hosts that record calls before sending, such as Pyramid, use these to report a call as not done instead of fencing it as unknown.
- `nanocode_mcp_tools::tool_output(result, server, tool)` is the conversion `PreparedMcpTool` uses from a `CallToolResult` to the model's `ToolOutput`, public so hosts that call MCP tools themselves, such as tempoxyz/pyramid's integrations, show results the same way and leave image limits to the runtime's image preparation (unsupported, undecodable or oversized images become placeholders before a model request). A result with image, audio or encrypted content is shown as that content even when it also has `structuredContent`, which stays the structured result; before, `structuredContent` won and the images were dropped. `value_output(result, server, tool)` does the same for a result held as JSON and shows a value that is no `CallToolResult` as JSON.
- `McpCallError::effect` says what is known of a failed MCP tool call's effects, so hosts that record calls before sending them, such as tempoxyz/pyramid, don't each classify the error: `Refused(message)` when the server or the host refused it before anything ran (a JSON-RPC error carried by a 4xx reply or whose code says the request was rejected before it ran: parse error, invalid request, method not found, invalid params or -32042 payment required, with its message; a 4xx other than 401 without one, as `HTTP <status>`; or, as `Refused(None)`, an `OAuthRuntime` refresh that failed before the request), `Unsent` when the request never reached the server (`TransportError::is_unsent`, a bearer source that could not give a token included, since the host that implements it knows why), `Unauthorized` for a 401 the transport could not resolve with a fresh token, and `Unknown` for anything that may have run: any other JSON-RPC error, such as an internal or implementation-defined error a server answers with a 2xx or at the end of an SSE stream after its handler started, a 5xx, a broken stream, a timeout or a payment failure. Every JSON-RPC error used to count as refused.
- `nanocode_mcp_tools::stdio::spawn(command, outgoing, inbound)` runs a newline-delimited JSON-RPC MCP server as a child process for any `nanocode_mcp::Session`: it pipes the child's stdin and stdout, starts it in its own process group with kill-on-drop, returns its stderr for the caller to drain or log, and stops the process group when the session's last handle is dropped. Hosts that drive one MCP stdio server themselves, such as Pyramid's Hand for its computer-use provider, use it with `Session::new` instead of a JSON-RPC loop of their own.
- MCP OAuth serves web backends as well as the native loopback login. `nanocode_mcp_http::oauth::discover_server` discovers an MCP server's authorization (an unauthenticated `initialize` POST first, because its 401 challenge carries the scopes to request and some servers answer a GET with 404 or 405, then the well-known probes) and `discover_issuer` an authorization server without an MCP server, each returning an `OAuthServer` with its metadata, resource indicator (none for an issuer) and scopes. `select_scopes` follows the MCP spec's order: the challenge's scopes, else the protected resource's, else the authorization server's, plus `offline_access` where offered; it used to request the union of the first two. `register_web_client` registers a confidential client (RFC 7591) with the first of `client_secret_basic`, `client_secret_post` and `none` the server supports, and honors the method the server assigns. `WebLogin::start` takes the host's redirect URI, scopes, extra authorization parameters and a state prefix and returns the authorization URL and a serializable `PendingWebLogin` the host keeps under its `state`; `PendingWebLogin::complete` checks the callback's state, client and `iss` (RFC 9207) and exchanges the code. The native `begin_login` runs on the same two steps. An empty resource omits the `resource` parameter from authorization and token requests. `ClientAuthentication::with_method` and `method` map RFC 7591 method names, `revocation_request` and `revoke_token` revoke a token (RFC 7009), and `token_endpoint_request` is public for refreshes a host schedules itself. `parse_token_response` accepts a missing `token_type`, a string `expires_in`, Slack's `authed_user.scope` when `scope` is absent, and a 200 that carries an OAuth `error` (GitHub); `invalid_grant`, `invalid_client`, `unauthorized_client`, GitHub's `bad_refresh_token` and a 401 without an error body are `TokenError::Rejected`, meaning sign in again. `McpOAuthCredentials::client` keeps a confidential client's secret and method, so `OAuthRuntime` refreshes such clients, and the native login stores the client it registered. tempoxyz/pyramid runs its integrations' sign-in and revocation on these, and their refreshes on `OAuthRuntime` over its own `McpOAuthStore` (sealed per-member token sets in Postgres, an advisory lock across backends). `oauth::http_client(user_agent, https_only, timeout)` builds the `HttpClient` a web backend passes these functions, with the rustls provider installed and no redirects, so no token follows one to another host.
- Web backends that run MCP OAuth themselves get its generic pieces: `OAuthServer::issuer` (the metadata's issuer without a trailing slash, which keys registered clients and token sets) and `OAuthServer::endpoints` (authorization, token, and registration and revocation when offered, for hosts that vet them, such as HTTPS only), `revoke_sign_in(http, endpoint, client, access_token, refresh_token)`, which revokes the refresh token when there is one, since that ends the grant, else the access token, and `PreparedMcpTool::listed`, the tool as `tools/list` gives it (remote name, description, input schema, readOnlyHint). `McpOAuthStore::authorization_required` is an `async fn` like the trait's other methods. tempoxyz/pyramid's integrations use them instead of their own copies.
- `OAuthRuntime` serves stored sign-ins without rediscovery and APIs other than MCP servers. `McpOAuthCredentials::token_endpoint` names the token endpoint the sign-in found, and refreshes go there without discovering the server's authorization again (and without checking its issuer against current metadata); `resource` sets the resource indicator refreshes send instead of the server URL, empty for none, as for an authorization server found by `discover_issuer`. Refreshes keep both. `OAuthRuntime::stored(server_name, server_url, http, store, credentials)` builds a runtime for such credentials, whose `server_url` only names it to the store, and `transport_from_credentials` uses it for them; `access_token` and the now public `refresh_after_rejection` give a host's own API calls the same refresh as MCP requests. `with_access_token(call, refused)` wraps one such call: it calls with the current token and, when `refused` says the API refused it, refreshes after the rejection and calls once more, calling `refused_after_refresh` when the refreshed token is refused too; tempoxyz/pyramid serves its Google Workspace tools through it. `McpOAuthStore::authorization_required` (a no-op by default) hears when only authorizing again helps: the authorization server rejected the refresh token (`TokenError::Rejected`), none is stored, or a server refused the token just refreshed after its rejection (`refused_after_refresh`, which the Streamable HTTP transport calls); transient failures don't call it, and a refresh that fails transiently before the token expires keeps using it. Refreshes join in process per store as well as server name and URL, since a host with a store per user, such as Pyramid, reuses server names; a store is its instance unless `McpOAuthStore::refresh_key` names it, which hosts that build a store per call (Pyramid) return, such as the member's ID, so their refreshes join too.
- Hosts that keep their own per-user credentials, such as Pyramid with each member's tokens in Postgres, authenticate Streamable HTTP MCP with `HttpAuth::Source` (`McpServer::bearer_source`): the transport asks the `BearerSource` for a token before every request, and calls `rejected(token)` with every token a server refuses with a 401 challenge. The first refusal of a request is retried once with the token `rejected` returns when it differs; a refusal of that retry is reported to `rejected` too and its result ignored, so the source can tell a refreshed token that is still refused (the sign-in is gone) from an expired one. A `token` error fails the request as unsent. `Mcp::prepared_servers` waits for discovery and gives each configured server its callable tools or its error (a server still pending after the discovery timeout, twice the longest startup timeout unless `McpBuilder::discovery_timeout` sets it, fails as timed out), so a host can offer the servers that answered and say which did not. `PreparedMcpTool::call` sends one `tools/call` within the tool timeout and returns the `CallToolResult` or a typed `McpCallError` (`Session` keeps the `nanocode_mcp::Error` with its unsent flag and status, `Timeout` means the outcome is unknown), so hosts that record calls before sending fence only unknown outcomes; `read_only()` is the tool's readOnlyHint.
- `ShellSessions::with_secrets(environment, secrets)` takes a `SecretEnvironment`, a function the sessions call on every `exec_command` for variables a host keeps outside the process environment and may change between calls, such as Pyramid's per-thread secrets on a hosted Hand. Each command gets them in its environment, never in its command line, after the fixed environment, and every value of at least 4 bytes (`MIN_REDACTED_SECRET_BYTES`; shorter ones such as `1` or `on` would garble all output) is redacted from that session's output as sensitive names' values are, whatever the variable's name. Hosts used to write them to a script, prefix each command with sourcing it and redact the output themselves.
- Shell commands and stdin writes carry the calling agent session (`ExecCommand::from_caller`, `WriteStdin::from_caller`; Codex's `exec_command` and `write_stdin` handlers set it from `ToolContext::session_id`). `ShellSessions::per_caller()` makes a process answer only the session that started it: `write_stdin` from any other session fails without touching the process. Hosts whose one shell runtime serves many sessions, such as Pyramid's Hand serving several threads, use it instead of keeping their own owner map; the CLI leaves it off so subagents may poll a process the root started.
- `ShellSessions::running()` lists the processes its sessions run right now as `RunningProcess` values, by session ID: the calling session from `ExecCommand::from_caller`, the command as written, the resolved workdir, the wall-clock start, and `in_call` while an `exec_command` or `write_stdin` call is waiting on it. A process is listed from its spawn, through its `exec_command` call and after it as a numeric session, and leaves the list the moment the sessions reap it, even when nobody polls it again, though its session stays until a poll collects the exit; termination and pruning remove it too. Hosts that show what a machine runs, such as the status socket of Pyramid's native Hand, read this instead of recording calls themselves and guessing which child process belongs to which session from the process table.
- `RuntimeBuilder::without_runners()` builds a runtime with no remote runners: its agents get no `hands` tool and no runner routing, runner management is off, and any configured runners or runner servers are dropped. Hosts that run every command on machines of their own through their own tools, such as Pyramid's backend (which also passes `without_cua()` and its own tools), use it so the model sees no runner surface it cannot use; the CLI keeps runners.
- `RuntimeBuilder::model_instructions(model, instructions)` gives one model its own system prompt in place of the runtime's or its harness's `instructions`, for the root and for every agent spawned on that model: aliases resolve to the catalog ID, the runtime resolves a root or cross-harness child through `Settings::model_instructions`, and each harness passes the map to `ClaudeBuilder::model_instructions` and `CodexBuilder::model_instructions`, which a same-harness child spawned with that model takes instead of inheriting its parent's prompt. Instructions a spawn sets itself (`SpawnBuilder::instructions`) still win, and a child that keeps its parent's model keeps its parent's prompt. Hosts tailor prompts to a model, and before, a same-harness child on another model was built from its parent's recipe and always got the root model's prompt.
- Project instruction discovery is shared by local and remote hosts: `PROJECT_INSTRUCTION_FILES` in nanocode-home lists the file names in precedence order (`AGENTS.override.md` hides `AGENTS.md` in the same directory), `instruction_scopes(paths)` turns workspace-relative paths into the directories whose instructions apply, the root `.` first and then each ancestor of each path, root to leaf without repeats, and `instruction_candidates(scope)` names the files to try there in order. `ProjectHome` reads them from the local disk; hosts that read a workspace elsewhere, such as Pyramid reading a Hand's files through its own tool, use the same functions and their own reader.
- `nanocode::http::origin` (`nanocode_http::layer::origin`) tells a host transport which work a model request continues. While an agent's model call is polled, `origin::current()` returns its opaque origin: the agent's host context, or for a root without one the durable operation of its turn, which is the prompt's request ID, a subagent completion turn's `subagent-completion:` ID or a compaction's operation ID, the same value its tool calls carry in `ToolContext::host_context`. Claude root tool calls now fall back to that operation as Codex roots already did, so a child spawned from either names its parent turn. A host's `Sender::send` and Codex `HostTransport` calls read it; it never enters a request's body, headers or logs. `origin::scope` holds it in a thread-local only while the scoped future is polled, so it follows that future across threads, never reaches other tasks, and is restored if a poll panics; Codex `ResponsesAttempt`s capture it when they are built and the Responses service restores it in its connection-owner task, which sends both HTTPS and WebSocket requests. Each WASM frame takes native stack that the shadow stack does not show (about 200 bytes against 14 of shadow stack per `JSON.stringify` level, 1,640 against 650 per nested `String(array)`), and how much native stack is left depends on the host (Node's `--stack-size`, workerd, the host frames below the module) and on the tier (Liftoff or TurboFan), so no fixed charge fits every host: the previous charge of 192 bytes per frame plus twice the shadow stack cut plain recursion to 858 calls and still trapped the instance in `JSON.stringify`, `String(array)` and getters under `node --stack-size=500` on 2026-10-24, and the 512 KiB shadow limit before it trapped Node 26 and workerd at 4,800 nested objects. It assumes 4 KiB per frame (the largest steps measured in Node 24 with Liftoff only and TurboFan only were 1.7 to 2.6 KiB, and a few frames reached 8.7 KiB): an answer of R bytes allows (R - 48 KiB) / 4 KiB more frames from where it was asked and, since every frame below is one of those frames, that many frames from the outermost one for every later path in the same entry, so repeated recursion within that depth asks again only after the entry ends. It first asks after 16 frames for 128 KiB and doubles each answer up to 1 MiB, so shallow cells pay one 128 KiB probe (about 10 us) per entry, and makes QuickJS throw `RangeError` once less than 64 KiB is left, enough to build the error. The host counts its entries into the module in the word at `entry`, and a changed count discards every answer, because each entry starts at a different native depth. Cargo does not rebuild `rquickjs-sys` when the header changes, so a host build must change `CFLAGS_wasm32_unknown_unknown` with it (nanocode-ts adds the header's hash). A rejection still unhandled after the microtask queue drains fails the cell with `Unhandled promise rejection: <reason>`, as Node exits, also after a yield, which `wait` then reports: the runtime's rejection tracker records rejected promises until a handler arrives, and `drain_jobs` passes those left to `runCell.uncaught`, which ends the cell. Such rejections used to vanish. `tools.*` promises stay observed, as upstream, so an unawaited tool failure stays silent, and `exit()` in a timer or an unawaited async function ends the cell as done.
- When a host gives `LocalCells` a prelude, the embedded engine installs `__nanocodeBytes` for it (`code-mode-engine/src/bytes.rs`): `put(string | ArrayBuffer, offset?, length?)` stores UTF-8 or bytes under a numeric ID, `take(id)` returns them as an `ArrayBuffer` that owns the Rust buffer (no copy), `text(id, fatal?)` decodes a stored buffer straight into a JS string without an `ArrayBuffer`, `discard(id)` drops one, and `decode`, `encode`, `toBase64` and `fromBase64` (lenient: URL-safe letters, no padding, other characters skipped) run natively. `nanocode_code_mode::code_mode::bytes::{put, take}` reach the same store from host tools, so a prelude passes IDs in tool inputs and results instead of base64 inside JSON. The prelude removes the global; without a prelude it is not installed. gakonst/nanocode-ts moves fetch bodies and `bash.readFile`/`writeFile` this way: on 2026-10-24 an 8 MiB fetch, write and read in one cell grew its module memory to 20.6 MiB instead of 651 MiB. `put` of a string encodes it in 1 MiB slices (cut before a high surrogate), each through `CString`, which borrows an ASCII string's own bytes, and turns a lone surrogate into U+FFFD as `TextEncoder` does, so it never holds a whole C-string copy beside the result. - A running cell streams its `text()`/`console` output: `observe_updates` sends the text items not yet streamed as one `CodeModeUpdate::Notification` on the cell's origin call (a delta, items joined by newlines), once the observation is 500 ms old and then whenever the cell's queued updates drain, so a cell that finishes quickly logs no extra events and a tight loop's lines arrive as one notification; at most 64 KiB is streamed per observation, the rest arriving with the result. - Use the same remote Code Mode protocol whether the brain initiates a connection or accepts a runner connection, on loopback or across machines. Keep socket and storage adapters replaceable for WASM hosts such as Workers; in-memory storage is not persistent durability. Preserve cancellation and report uncertain remote outcomes without silently replaying dispatched work.
- `nanocode_code_mode::remote::RemoteClient` owns the brain side of the remote Code Mode protocol on every target: pending replies, brain and hand callbacks, detached cells and their turn generations, cancellation, operation deadlines and unknown outcomes after a disconnect. `RemoteClient::new` runs it over any `RemoteLink`, which only sends and receives frame batches and closes the connection, and returns a driver future the host spawns. `SocketTransport` in integrations/tool-runtime is the native WebSocket link with dialing, accepting, heartbeats, liveness and close frames; WASM hosts implement `RemoteLink` over their own sockets. Frames that start or settle work are `RemoteDelivery::Durable`, so a host can make its state durable before sending a batch that contains one; relayed hand calls and their results are `Immediate`. `RemoteFrame::dispatches` marks the requests that start or continue work on the peer (Execute, Wait and Call), so a host can refuse to send them, for example once a turn's cancellation is requested, without decoding frames itself. `RemoteCatalog::decode` reads the catalog a hand or runner publishes as its first frame, with its tool definitions and advertised name, and rejects any other first frame with `NO_CATALOG`; the native `SocketTransport` and WASM hosts use it alike, so a host that stores the catalog across hibernation keeps it as opaque text. `RemoteLink::changed` runs after each received batch and finished callback, `RemoteActivity::busy` reports running callbacks and detached cells for host idle checks, and `RemoteActivity::is_alive` reports whether its client still exists. A link that wrote none of a batch, such as a host refusing it for a revoked hand or a cancelled turn, fails `send` with `CodeModeHostError::unsent`; when the connection ends, operations whose request no link accepted, or a link refused that way, report that they were not dispatched, and only requests a link may have written report unknown outcomes. A link that refuses only some request frames of a batch, such as a host that shares one link among turns and stops one turn's dispatches, writes the other frames and fails `send` with `CodeModeHostError::refused(reason, ids)`: the client counts the rest of the batch as written, fails only those requests' operations as not dispatched and keeps the link and its other operations running; refusing an ID that is not a request of the batch fails the link like any other send error. `RemoteLink::max_frame_bytes` is the largest frame both ends accept: `SocketTransport` and the WASM package's link take the smaller of their own policy and the `max_frame_bytes` a hand or runner publishes in its catalog, and every request carries it, so the hand learns the brain's limit. No side writes a larger frame: the brain fails an oversized request as not dispatched and replaces an oversized callback result with the limit error; a hand replaces the inputs and outputs of an oversized result's nested calls, and then its output, with the limit error while keeping its cell, sends oversized nested-call updates without their payloads and fails an oversized cross-hand call without dispatching it. Before this, one 1.5 MB `text()` or cross-hand `Write` on a Worker hand closed the connection and failed every pending call with an unknown outcome. Execute, Wait and Call deadlines add the operation's requested `yield_time_ms` (a Call's from its input, such as a `write_stdin` poll of up to 300 s) to the operation timeout, because a model-chosen yield longer than the host's timeout otherwise expired the deadline and cancelled the turn's cells or reported the call's outcome unknown. Each client starts its request IDs at a random offset below 2^52, so when a host hands a connection to a new client, as the Worker does for a runtime reopened after a failure, a late reply to the previous client's request cannot reach the new client's request with the same ID. A client knows only the cells its own requests started: when a host hands a live connection to a new client, as the Worker does after a forced Durable Object restart while a hand stays attached, the hand keeps running the previous client's cells, and the new client drops their `DetachedUpdate` and `DetachedComplete` frames, so their completion notices are lost, answers their brain callbacks as unavailable, never answers a callback the previous client was still running, which then waits for the hand's callback deadline (`nanocode hand` sets none), and sends turn controls such as CancelTurn only to hands it has used itself; a Wait on such a cell's ID still reaches the hand through the session's placement. Reporting or cancelling those cells needs the hand to learn that its client changed, or durable records of each session's hands and cells.
- `RemoteOperation::EndTurn { session_id, turn_id, hook_event_name }` tells a remote hand that a turn ended, so its tools release what the turn held: the native hand (`Hand::connect`) calls `Tool::end_turn` on every registered tool, whether or not it runs cells for the session, logs a tool's failure without retrying it, and answers `Ok(None)`; it dispatches nothing, so links that send only tool calls pass it. It is the remote counterpart of the attachment protocol's `EndpointFrame::TurnEnded`. Hosts send it with `RemoteClient::request` once they know a turn ended; tempoxyz/pyramid's broker sends it (`hook_event_name` `Stop`) for turns that ran browser steps, so the Hand's ChatGPT-extension bridge closes their tabs. A hand built before it fails to decode the frame, so send it only to hands built since.
- A hand whose catalog carries a `runtime_id` keeps its work across reconnects when its brain opts in: its catalog says `resumable: true`, and a brain whose `RemoteLink::resumes` returns that runtime ID marks every request `resumable`. `Hand::connect` owns one executor for its whole run, so once a resumable request arrives a dropped socket no longer cancels the session runtimes, their processes or running cells, and a brain that wants a session gone ends it with Cancel. The hand keeps each resumable request's reply until the brain's `Ack`, which a client built with `RemoteClient::new` sends for every batch of replies it receives, and answers requests that finished while it was away on the next connection. A resumable link survives reconnects itself, stays open and passes each later catalog to `RemoteClient`, which sends `Resume` with the requests it wrote and still waits for: the hand resends their replies in full form, because compact replies may name nested-call updates lost with the old socket, leaves running ones to reply when they finish, answers ones it never received with `NOT_RECEIVED` (not dispatched) and forgets the rest; a catalog with another runtime ID fails the client with `HAND_RESTARTED`, so only that runtime's outcomes are unknown. A new client sends an empty `Resume` first, so a hand forgets replies no client waits for, unless it is built with `RemoteClient::resuming`. Cancel and CancelTurn also end a session's in-flight Call requests, which reply with `CALL_CANCELLED` (unknown outcome), because a Call runs one nested tool outside any cell and nothing else could stop it; a process it started may outlive it. A `CancelTurn` with `turn_id` ends only the Calls whose context names that turn and leaves the session's cells alone; without one (the field is omitted on the wire, as before) it cancels the session's turn as it did. A 410 at the WebSocket upgrade rejects a hand's credential for good, like 401 and 403, so a revoked hand stops instead of redialing; `Hand::run` reports it as `HandEvent::Rejected { status }` before returning the error, so hosts match the event instead of the error's text. Callbacks in flight when the socket drops fail with an unknown outcome, and updates sent while it is down are lost. Brains that do not opt in, the native `SocketTransport` and pool-managed executors among them, see no change: their hands still cancel every session at disconnect. On loopback (a brain whose link outlives sockets and a `nanocode hand` with workspace tools), dropping the socket 1 s into a 3 s `exec_command` Call, a cell whose nested `exec_command` takes 2 s and a background process polled afterwards: before, the hand cancelled every session and the brain failed with `unexpected runner frame` and unknown outcomes; after, the hand reconnected in 100 ms, the Call and the cell returned their real outputs 2.0 s after the drop, and the background process kept running and printed its remaining output.
- A brain that outlives its process, such as a server whose hands reconnect to whichever replica holds their socket, resumes its predecessor's requests with `RemoteClient::resuming(link, timeout, pending)`: its link's `send` sees every Request frame with its ID and the host's `RemoteContext::call_id` before the write, so the host persists that pair there, and after a restart it passes the IDs still unsettled for a link whose `resumes` names the same runtime. The client sends them in its first `Resume` instead of an empty one and returns one `ResumedReply` per ID: the hand's retained reply in full form, the reply when a running request finishes, or `NOT_RECEIVED`, which every reply path surfaces as `CodeModeHostError::unsent`, so a write lost with a dying socket is known not to have run without a separate delivery acknowledgement. Such a client sends no `Ack` itself: the host calls `RemoteClient::ack` with a request's ID once it has durably settled the reply, so a successor resumes every ID whose outcome its predecessor had not recorded and gets the retained reply, never `NOT_RECEIVED` for a request that ran. A link without `resumes` answers each ID with `HAND_RESTARTED` (unknown outcome). A reply's value has its nested calls expanded from the compact field forms, as `request` expands them, while updates are ignored because the full form names none and a successor never saw the updates its predecessor received, so an Execute or Wait reply deserializes as `CodeModeExecution` and a Call reply decodes with `output_from_wire`, as `call`'s value does; before, it was the raw compact value, and on loopback a resumed cell whose nested call returned JSON failed to deserialize with `missing field output`. Only one client may hold a runtime's unsettled IDs, because each `Resume` makes the hand forget replies it does not name. On loopback, a brain dropped 0.7 s into a 2 s Bash Call and a new client built with `resuming` on the hand's reconnect got the Call's real output 2.05 s after it started, and an ID the hand never received came back unsent.
- `nanocode_code_mode::remote::serve_queue(link, queue, sent, options, failed)` serves one hand socket from a host's durable command queue, for brains such as tempoxyz/pyramid's broker whose calls are queued in a database and may be sent by whichever replica holds the socket. The host implements `CommandQueue`: `poll` returns the queued calls still allowed to run (`QueuedCall` with a host `Origin`), the turns of sent calls to cancel and the turns to tell when they end, skipping calls already in flight; `admit` records each request ID with its call before the write, all or none, and an error refuses the write as `CodeModeHostError::unsent`; `recorded` says whether a call is still queued and its request ID; `settle` stores a `Settlement`; `turn_ended` answers whether a watched turn stopped; and `unsettled` hears settlement failures, which leave the call pending. The function builds `RemoteClient::resuming` over a link that admits Call frames before writing and refuses every other dispatching frame, settles the replies of `sent` requests and of each dispatched call (a reply is `Completed` with its wire output, an unsent failure of a recorded call is `Requeue`, a failure while the client has a failure is left for the next socket, a failure of a call never recorded is `Unavailable`, and anything else is `Unknown`, never retried), acknowledges a reply only after `settle` stored it, sends one `CancelTurn` naming the turn (`turn_id`) per session and turn and one `EndTurn` (`Stop`) per watched turn that ended, checking at `QueueOptions::end_check`, polls every `QueueOptions::poll`, and returns the driver's reason when the connection ends or the host's error when `poll` or the `failed` future (such as a heartbeat) fails.
- Remote Code Mode payloads cross the connection once. Brains mark their Request frames and hands their Callback frames with `compact: true`, and only answers to a marked frame use the compact forms, so peers built before them keep sending and receiving the full ones: a tool output omits `output` when it is the JSON text of its `structured_result`, as `ToolOutput::from_json` makes it, and the receiver encodes the value again; a nested call omits `structured_result` when it equals `output` and `output` when it is the JSON text of `structured_result`; a completed update omits the input that the call's start update on the same request carried; and a reply names each nested call whose completed update the same request delivered as `{"call_id","delivered":true}`. `SentCalls` writes them on the hand and `ReceivedCalls` in `RemoteClient` restores them before an observer or the execution sees them. A tool output whose `structured_result` equals its `output` crosses with a null `structured_result` to every peer, because every build derives the structured result from the output then. A value holding floats is compared with its JSON text after a parse and a second encoding, because serde_json's default float parsing does not round-trip every value.

- `SessionLog` and `SqlStore` version their storage formats. Each owns an ordered, append-only list of `Migration`s per dialect and records the number it ran in the shared `nanocode_formats` table under its component name (`session_log`, `records`), so several components can keep tables in one database. `SessionLog::migrate()` and `SqlStore::migrate()` run the missing migrations, each with its version update in one host transaction, and fail with `StoreError::UnsupportedFormat { component, stored, known }` without touching the tables when the database records a format newer than the build's `FORMAT`; both still migrate on their first operation when the host did not call `migrate`. Hosts call it where they open storage, so a host that runs several builds against the same data, such as Pact's Durable Objects during a deploy (an object can be reached by the previous Worker version for a while, and threads are kept indefinitely and migrate forward), refuses storage a newer build wrote instead of reading a format it does not know, and can surface that refusal as a retryable error at a point it controls. - `SessionLog::replace_queued(request_id, edit_id, text)` edits a queued turn's prompt in place for hosts whose users revise a message waiting behind a running turn: the text replaces the prompt's first text input and drops its other text inputs, while its images and other inputs, their order, its transcript and hand, its request ID and its place in the queue stay. The update and its receipt, a `replaced` event naming `edit_id` and the digest of the edit's text, commit in one transaction, so `Replaced::Applied(Some(event))` comes back once and a retry with the same edit ID and text answers `Applied(None)` whatever state the turn reached since, without undoing a later edit; the same ID with other text is `Conflict`, a turn that is not queued and holds no receipt for the ID `NotQueued`, and an edit whose row, receipt or input.accepted event would exceed `logical_limit` `TooLarge`; an edited prompt above `value_limit` spills into `log_parts` in the edit's transaction as a submitted one does. The update is conditional on the prompt digest it read, and when another writer changed the prompt in between it reads the turn again and applies the edit to the new prompt. A submit retried with the original prompt after an edit reports `Conflict`, since the request ID now holds other content. `TurnInbox::move_queued(queued_id, target)` moves a queued prompt into the running turn as an identified steer under the queued turn's request ID and then dequeues the turn as cancelled with `steered: true` (`SessionLog::withdraw_steered`, conditional on the digest that was steered). The running turn's durable steer receipt is the only decision: `Agent::steer_receipt(id, prompt)` (`LifecycleBackend::steer_receipt`, `DurableSession::steer_receipt` for both backends' policies) answers `SteerReceiptStatus::Accepted`, `Absent`, `Different`, `Withdrawn` or `Unknown` from the session's identified steer receipts, `Absent` only when the driver holds every receipt (no terminal receipt limit, sealed receipt pages loaded, history never pruned) and `Unknown` otherwise or without a durable policy, and `drive` withdraws instead of running a queued turn whose ID already has an `Accepted` receipt for its prompt. So a crash between the steer and the dequeue neither loses nor repeats the prompt, and repeating the move answers `MovedQueued::Moved`; `NotRunning` leaves the prompt queued, `Conflict` means a steer under that ID carried other input or was withdrawn, and `Unknown` moves nothing. A moved prompt shares the running turn's outcome, and one edited after its steer was accepted stays queued and runs its new text.
- `SessionLog::value_limit` is the host's physical UTF-8 binding and row budget; `logical_limit` separately retains the optional prompt admission, event omission and result failure policy. Only owned event-body and prompt slots spill into immutable content-keyed `log_parts`, in the same transaction as their row; each part fits the physical budget including its key and SQLite record header, is verified against its BLAKE3 key when read, and is never replaced or deleted. Reference-shaped user bodies are stored as parts too, and only owned read columns are decoded. Imported prompts spill before JSON batching, whose bindings respect the physical limit; an imported row that cannot fit fails before writing. Small values keep the same row writes. `page_bounded(after, limit, max_bytes)` budgets decoded event JSON UTF-8 bytes before loading parts, excludes the crossing event except that the first event is always returned (also for zero bytes), and leaves the cursor on the last returned event; envelope bytes are outside the budget. Inline logs remain readable; binaries without this contract cannot read spilled values. Bounded pages require a positive event count.
- `SessionLog::logical_limit(bytes)` optionally bounds logical row and event sizes independently of physical storage. Rows are sized conservatively by SQLite's record format (https://www.sqlite.org/fileformat.html#record_format): one varint for the header size and one per column, at most 9 bytes each, the text columns' bytes and at most 8 bytes per integer column. `append` logs an event above this logical limit as `{"type":"omitted","request_id","source","event_type","bytes"}`, and `finish` records an oversized result as a failed one whose error names its status and size. `submit` answers `Submitted::TooLarge { bytes, limit }` without writing when the logical turn row or its input.accepted event would not fit; that event is sized as `TurnInbox` stores it, with the request ID, UUIDv7-length identifiers or the request ID where a resumed turn uses it as its turn ID, and its seq at u64::MAX. Notes and retry errors that hosts add to an unfinished turn are not reserved or spilled and remain subject to the host's physical SQL row limit.
- `SessionLog::blobs(store, threshold)` gives a log the host's `SharedBlobStore` (Send + Sync on WASM too, because `TurnInbox`'s sink is an `EventSink`), so no SQL row holds image bytes or a value above the threshold. `submit`, `replace_queued` and `import` store each base64 data-URL `UserInput::Image` of a prompt as a `BlobUrl` (the decoded bytes under `BlobKey::of`), found with `BlobUrl::from_data_url` before anything is stored, so a `TooLarge` answer puts nothing. The submission digest stays the BLAKE3 of the host's prompt, so a resubmitted data-URL prompt is the existing turn; an edit's digest is of the edited stored prompt. `TurnInbox` hands the runtime the stored prompt, whose BlobUrl images the runtime loads. An event body or prompt above `threshold` UTF-8 bytes, or above `value_limit`, becomes one blob referenced as `{"$nanocode_log":["b3:<hex>"],"bytes":N}` instead of `log_parts` parts, and `page`, `page_bounded`, `turn_page*`, `turn`, `pending` and `import_events`' comparison re-materialize it; BlobUrls inside prompts and event content come back as stored, for hosts to serve from their own store. Every blob is put before the transaction that references it, so a failed put commits nothing. The SDK never deletes blobs: the host owns a session's blob namespace, deletes it with the session and copies the referenced blobs before importing a fork. `log_parts` references written before keep reading, a log without a store behaves as before, and binaries without this contract cannot read blob references.
- `SessionLog::page_bounded` and `turn_page_bounded` size a page without reading the bodies it skips. The window runs over each candidate's `seq` and a lower bound of its decoded size: `octet_length(body)` minus `LONGEST_SINGLE_KEY_REFERENCE`, the 118 bytes of a reference with one `b3:` key and a 20-digit `bytes` field. SQLite (3.43 or later) and PostgreSQL (`textoctetlen` reads only the TOAST header) answer that from the row header. The query then joins `events` for the rows whose running bound fits, and `read_bounded` applies the exact rule before loading any reference: a reference counts its `bytes`, any other body its UTF-8 length, and the first event is always returned. The bound never exceeds a row's decoded size. Inline bodies count exactly and single-key references count 0. A multi-key reference fits only a physical row limit of at least 304 bytes (a 163-byte two-key reference plus 141 bytes of turn-row overhead), so each of its parts holds at least 213 bytes, more than the 67 bytes per key it adds. Pages, `rows`, `has_more` and cursors are therefore unchanged, and the bodies read beyond a page total at most `max_bytes` plus 118 bytes per candidate.

- Third-party storage implements one host interface and leaves every durability rule to core/durability. `KeyValueStore` runs over a linearizable `KeyValue` (get, put_values, compare_and_swap and an optional list_keys). `SqlStore` runs over a SQLite or PostgreSQL `Sql` host whose `transaction(operation, statements)` executes the SDK's statements with text parameters atomically and returns each statement's rows; Durable Objects, D1, libSQL and sqlite-wasm need nothing else. SqlStore owns the `states`, `owners`, `blobs` and `records` tables, which are the nanocode Worker's layout and are created by `SqlStore::migrate` or on first use, and every statement: acquisition increments the fence in SQL, a replacement inserts its records and head only while the owner, fence and expected revision match, and only while every record it staged is present under its state and key, and only when it replaced nothing reads the head in a second query to report Fenced or Conflict (it used to read the head in every replacement transaction, one statement and two row reads per commit that only a refused commit needed), and commit_many sends a group in one transaction with independent outcomes. Counters are decimal text so JavaScript hosts keep u64 revisions, and the fence stops at SQLite's INTEGER maximum. It reports no concurrent handles, so SharedStore groups concurrent commits into commit_many. Records go to `blobs`, a rowid table whose `id` is the first 8 bytes of BLAKE3(state ID, a zero byte, key) as a signed integer, so a lookup is a rowid probe without a second index and rows up to about 4 KB stay in their leaf page. The `WITHOUT ROWID` `records` table that builds before 2026-10-21 wrote (primary key state ID and key) is still read as a fallback and never written; an index b-tree keeps at most about 1 KB of a row in its page and puts the rest on an overflow page of its own, so rows of 1-4 KB, most of a session's records, left a third of the table unused. Two keys whose ids collide leave the second unstored, and the replacement that staged it then fails instead of committing a head that names a missing record.
- `BlobStore` (core/durability, re-exported as `nanocode::durability::BlobStore`) is the host's store for large immutable bytes, keyed by `BlobKey` (`b3:` and the BLAKE3 hex of the raw bytes). `put` resolving Ok means the bytes are durable, and putting a key again is harmless; `get` returns the bytes or None, and `get_blob` checks them against their key. `BlobUrl` names media whose bytes are in the store as `nanocode-blob:<media type>;b3:<hex>`: `store_data_url` decodes a base64 data URL and stores the raw bytes, and `load_data_url` rebuilds the data URL. The SDK puts a blob before it commits any record that names it and never deletes one: a host keeps each session's blobs in a namespace of its own and deletes it with the session, and a crash between a put and its commit leaves a blob no record names. `MemoryBlobStore` (runtime/durability) keeps blobs in memory for tests and hosts without persistent storage.
- `Sql::dialect` names the SQL its host runs: `SqlDialect::Sqlite` by default, so existing hosts are unchanged, or `SqlDialect::Postgres`, for which `SqlStore` and `SessionLog` (and so `TurnInbox`) send PostgreSQL statements over the same tables and parameters: `$n::text` placeholders, BIGINT identity columns instead of rowids (`states.ord` keeps `list_states` newest first), `json_array_elements` and `->>` instead of `json_each` and `json_extract`, `GREATEST`, `IS DISTINCT FROM`, `information_schema.columns` for the retry column check, `json_build_object` for the retry fields, which keeps their order, and every result column cast to text, so a host returns each column as an optional string; PostgreSQL resolves an unqualified `ORDER BY seq` to the text output column of `CAST(seq AS TEXT)` and sorts `1, 10, 2`, so ordered statements name the table column (`events.seq`, `turns.first_seq`, and `sized.seq` for the outer sort of the byte-bounded event and turn pages). A PostgreSQL `SqlStore` has no legacy `records` table, and its log's `MAX(seq)` lookups are limited to the scope, so a host that serializes a scope's writes (as SQLite's single writer does) gets the same `first_seq` and `last_seq`. Its migrations run through `migrate` or on first use like SQLite's; `CREATE TABLE IF NOT EXISTS` can race between PostgreSQL sessions, so hosts with migrations create the tables first, and a host whose database already has `turns` or `events` tables keeps a log in another schema. `nanocode_store_postgres::PostgresSql` is the tokio-postgres host, running each statement group in its own transaction. PostgreSQL `SqlStore` record inserts and replacements check the owner with `FOR SHARE` on its `owners` row and the replacement's upsert updates only the expected revision, so at the default READ COMMITTED an acquire waits for an uncommitted replacement and then sees it, and a replacement whose owner was fenced or whose revision moved inserts nothing and reports Fenced or Conflict. `SqlStore` is a `StateStore` for any host lifetime, so a host can run it on a transaction it borrows.
- `nanocode-store-sqlx` runs `SqlStore`'s PostgreSQL statements on sqlx 0.9 (the version tempoxyz/pyramid's backend uses, so a host builds one sqlx): `SqlxSql` over any `PgConnections` source (a `PgPool`, or a host's own connections that wait out restarts) runs each statement group in its own transaction, `SqlxTransaction` runs them on a `PgConnection` inside a transaction its caller commits, and `commit_staged(writes, connection)` commits a `StagedStore`'s writes there, so staged session state commits with the host's own transaction. Each column comes back as an optional string, as `SqlRow` expects. It builds natively only, like `nanocode-store-postgres`.
- `StagedStore::new(base)` wraps any `StateStore` and keeps every acquisition and commit in memory: reads see staged states and records before `base`, acquisitions read `base`'s owner without fencing and stage the next fence, and `StagedStore::writes` returns the `StagedWrites` handle the host keeps. `StagedWrites::commit_to(store)` acquires each changed state in `store` for its staged owner, fails with `Fenced` unless that fence is the one staged (no one acquired it since) and with `Conflict` unless the revision is still the one staging started from, then replays every staged commit in order, the records with the first, so revisions, which durable state payloads embed, match what the session saw. `commit_to` leaves the writes staged, so a host whose transaction fails to commit can call it again on a new transaction; the host calls `discard` once its transaction has committed, and a `commit_to` after that commit fails with `Fenced` instead of writing twice. Staged states have no events or summaries. Give `commit_to` a store that runs on a transaction the host commits or rolls back, such as an `SqlStore` over the host's transaction, so state commits atomically with the host's own writes: tempoxyz/pyramid opens each turn's `SessionStore` over a `StagedStore` of its PostgreSQL `SqlStore` and commits the staged writes in the transaction that sets the turn's final status, only when the turn succeeds, discarding them after that transaction commits, so a failed or cancelled turn leaves the model context of the last successful turn. A session over a `StagedStore` ends when its writes are committed or dropped.
- `SessionStore::export_branch(id, at)`, `export_page` and `import_branch` move a settled branch into an independent store, which the same-store `branch` cannot do, for hosts that keep one store per conversation, such as a Durable Object per thread that forks a thread into a new object or runs a throwaway fork for a review. `BranchExport` is small: the source record, the boundary, the selected checkpoint's key, the number of covered turns and the key of an inherited-turn index, a `Sequence` of `{turn, checkpoint}` records (with `before` where the checkpoint before a turn is not the previous turn's, as at an import's first own turn) behind a record that also names the history's start. `export_page(id, export, cursor, max_bytes)` recomputes the covered history from the source on every call, so the source keeps nothing between pages, and fails when retention or a rewrite changed it; its pages walk the start checkpoint, the settled checkpoint of every covered turn, the selected checkpoint and the index, each as the physical records its root reaches (inline payloads, manifests, tree nodes and chunks) minus those the previous root reaches, in key order, and hold at least one record and stop before the record that would pass `max_bytes`. Records are found by following keys held as JSON strings, which is how `EncodedPayload` serializes, so every checkpoint format transfers without format code, and a page call keeps only the key graph of the checkpoints it walks and reads the previous root's records once, instead of a key list for the whole history or a walk per turn. The imported record keeps the index key, not a growing metadata list, so the copy can be branched in its own store or exported again through the turns it inherited, after its source is gone: Through takes the entry's checkpoint, Before the checkpoint before the entry, the history's start or the checkpoint the import began from. Exports allow pending operations after a Through or Before boundary and refuse Latest while any is pending. `import_branch` acquires the target once and commits a staged head whose record holds the import's next cursor; `SessionStore` treats that head as absent (load, resume, turns, list and branch), and a session described over it replaces it. `BranchImport::import(page)` verifies every record against its content address and its kind's size bound (inline payloads and manifests below 16 KiB, chunks at most `CHUNK_MAX` plus a UTF-8 boundary), rejects records it cannot verify, such as the chunked payloads of SHA-256 builds, ignores a page that ends at or before its cursor, refuses one that starts after it and commits the page's records with the advanced cursor in one fenced commit, so a host that loses an import calls `import_branch` again and continues from `next()` without counting SDK rows. `publish` refuses an incomplete import, hydrates the selected checkpoint and checks every indexed checkpoint root, then makes the session visible in one fenced commit; `import_branch` of an export already published returns it without writing. The session log moves separately, through `SessionLog::import` and `import_events`.
- `SessionLog::import_events(after, events)` writes the events another log's `page` returned under their own seq, request ID, creation time and body, so a host that forks a conversation into a new store, such as a Durable Object per thread, copies its log as well as its durable state: with `import` given each copied turn's `first_seq` and `last_seq`, which keeps it from synthesizing a result event, the target's `page` and `turn_page` answer the source's events for the copied range and its turns report the same results. `after` is the cursor the events follow, as `page(after, limit)` takes it; the events must ascend above it and fit `logical_limit`, bodies above `value_limit` spill into `log_parts` as appended ones do, and the call answers the last imported seq, the cursor for the next page. A read transaction finds where the target's log ends and reads back the rows in the range, and the import is refused before anything is written when the log ends before `after`, holds a different event at an imported seq (every column is compared, a spilled body after reading its parts back), holds an event of its own in the range that the import lacks, or another scope owns an imported seq. A write transaction then inserts the remaining events in order, each only while the log still ends at its predecessor, which is a primary-key lookup instead of a scan of the scope, so a replayed or retried import writes nothing and continues where a lost one stopped, and an append that lands between the two transactions fails the import instead of interleaving with it. On PostgreSQL the write also moves the `events` identity sequence past the imported seqs with `setval`, because explicit values do not advance it and the next `append` would collide. The seq is the primary key of an events table that every scope in a database shares, so the copied log needs seqs that no other scope in the target uses, as a fresh store per conversation provides. Copying with `append` cannot do this: it renumbers events, replaces their creation times and duplicates them when retried.
- StateStore: `peek` is required, because SessionStore::load, resume, branching and child journals read through it without fencing, and `owner` reports the current owner token without fencing; its unsupported default makes AgentRuntime treat a live agent's ownership as unknown. `acquire_with` runs its owned, synchronous StoreUpdate once against the acquired state; updates only calculate, None acquires without changing the revision, and the default acquire-then-replace reports failures after acquisition as Backend errors. `acquire_with_companion` acquires a distinct companion with the primary: an equal companion is NotCommitted before any write, NotCommitted means neither state changed, any other error leaves both uncertain, and a batching adapter validates both fences and revisions first and acknowledges only once the whole batch is durable. `commit` checks the fence and revision like `replace`, replaces the payload, advances the revision once, inserts absent records and appends events atomically; conflicting record content or a seq overflow is NotCommitted before any write, the default rejects events with NotCommitted, and events take contiguous seqs after the state's last, from 1, never reused. `commit_many` returns one result per commit in order, each judged on its own fence and revision; a shared write acknowledges none before it is durable, and a failed group may leave any subset committed. `supports_events`, `supports_summaries` and `batches_companion_acquisition` stay fixed per adapter and wrappers forward them; `concurrent_handle` returns a handle only when operations stay correct concurrently, including on one state; `flush` is an ordered barrier. `list_records` returns every record key of a state, for repairs that must find records by content; it is unsupported by default, and SqlStore, KeyValueStore (over `list_keys`), JSONL, SQLite and Postgres implement it and SharedStore forwards it.
- StateReader never acquires, fences or changes a revision: `read_state`, `read_records` and `read_events` are strongly consistent per state, while `query_states` and `query_events` come from an index that may trail commits. A summary belongs to the revision that committed it; index updates are idempotent by (state_id, revision) and (state_id, seq), Remove keeps a tombstone that queries never return, and an asynchronous indexer persists the publication intent in the commit's transaction. `query_states` orders by (updated_at_ms, state_id) and `query_events` by (at_ms, state_id, seq), both descending, and `read_events` by seq between exclusive bounds; pages are live keyset pages, a zero limit returns an empty page, `usize::MAX` is valid and adapters impose no hidden caps. scope, parent, state_id and attributes match exactly, kinds match any listed kind, and text is an ASCII-case-insensitive literal substring of the title, preview or event texts.
- Payloads are BLAKE3-addressed: one inline `b3:` record under 16 KiB, otherwise content-defined `c:` chunks under a manifest keyed by its own hash. A manifest that would reach 16 KiB becomes a tree cut where a hash prefix is divisible by CHUNK_AVG / 64, so a save rewrites only the groups around its edits: on a 60-turn, 4 MB local Claude session manifest bytes fell from 2.39 MB to 1.55 MB. Keys without `b3:` are SHA-256 records from earlier builds that still load and verify, and `EncodedPayload::matches_key` treats a SHA-256 key of the same content as equal, so receipts and step inputs recorded before the change still match. Records are immutable and never deleted, so a session driver counts every record its loads read (the latest checkpoint at agent acquisition and `LoadPayload(s)`, through `EncodedPayload::load_noting` and `load_many_noting`) among its committed records, and the first save after a restore stages only chunks the load did not read: before, it resent every chunk of a re-encoded checkpoint, and in the Worker's `measure-store.mjs` on 2026-10-20 a Claude turn restored after 60 turns of 200 text deltas sent 172 statements and 2.29 MB over the WASM bridge, against 71 and 1.31 MB now and 70 and 1.24 MB for a warm turn, and took 43.0 ms instead of 48.3 ms. `SessionStore::load` keeps the checkpoint payload it read and the record keys that load noted, `prepare_resume_loaded` hands them to the session with the checkpoint preload, and the driver's agent acquisition uses them instead of reading and verifying the checkpoint again while the state's latest checkpoint key still matches, since records are immutable; the Claude backend takes the loaded value from the preload as Codex does instead of decoding the payload again. The load also notes the records a format's `CheckpointFormat::hydrate_noting` reads, Codex's history pages and items, and `DurableSession::take_checkpoint_preload_with_records` hands them to the Codex backend, which remembers them instead of re-encoding and hashing the whole history to check the checkpoint key; `load_many` reads the manifest levels and chunks of every payload it loads in one store read per level instead of one per payload; `prepare_resume_loaded` skips its head peek when the load found a session record; and `StoredSession::checkpoint_thinking` reads Codex's thinking without converting the checkpoint.
- Durable state transactions grow with their content, not with history: `EncodedPayload` binds at most one chunk (under 32 KiB) per record and `SqlStore::replace` sends one statement per new record, but an image held inline still costs a megabyte-scale transaction and its whole size again on every reopen, which a blob store avoids.
- Step inputs and outputs under 1 KiB (`STEP_INLINE_BYTES`) that a driver holds with their content are written inside the state row as `"=<json>"` instead of as `b3:` records, so a step's payload costs no row of its own: a model call's `{"wire","blake3","bytes"}` input, its output that references the message records, and a tool call's input. `OperationState`'s staging keeps their content, since the state row is rewritten on every commit while the step lives, and still stages their child records. Steps retire at the next `ExecutionAdvanced` or completion, so an idle session's head carries none. A head with any inline step has state format 6, which older builds refuse as an unsupported state format instead of failing on a missing record, and other heads keep format 4 or 5, so a rollback reads every session that is not mid-turn. In a Node sqlite harness on 2026-10-25 (nanocode-ts Code Mode, trivial `text("ok")` cells) a cell committed 5.1 rows and 10.1 statements to the store instead of 8.1 and 15.1 (with 5 event rows either way), and in the Worker's `measure-store.mjs` a Codex turn with three tool rounds wrote 58.5 Durable Object rows instead of 64.5 and read 176 instead of 224.
- `Sequence` in runtime/durability stores a list as one content-addressed record per item: each run of 16 item references is sealed into an immutable group page and each 16 pages of a level into a page of the next, and the payload holding the sequence keeps `{"tail":{"levels":[...],"items":[...]}}` with fewer than 16 unsealed references per level, so a save writes its new items, at most one page per level and references that grow with the logarithm of the length. `PagedWriter::sequence_cached` builds Codex histories this way and `seal_sequence` builds a sequence from already encoded items. `load_sequence` reads each level in one batched load and still reads the chained 64-item pages (`{"tail":"<key>"}`) of earlier builds, whose every save rewrote the tail page, while older binaries fail to parse a sealed tail instead of reading an empty history. `EncodedPayload::with_payloads` attaches the records a payload references, and the driver stages only those its committed records lack, including records its loads read, so callers need not track what is durable.
- The SDK's Claude durability policies set `ClaudeExecutionPolicy::pages_messages`, so root checkpoints and cursors are version 3: each conversation message and each retained Code Mode round (`conversation.code_calls`) is its own record, cached on its `HistoryMessage` or `CodeRound` beside its JSON, a checkpoint is `{"provider":"claude","version":3,"messages":<Sequence>,"code_calls":<Sequence>,"admitted_tool_ids","unadmitted_tool_ids","snapshot":<version 1 snapshot without them>}` and a cursor `{"version":3,"messages","code_calls","admitted_tool_ids","unadmitted_tool_ids","pending":<the whole working list>,"template":<record of the template's system and tools>,"cursor":<version 1 cursor without them>}`. `admitted_tool_ids` lists, sorted, only the admitted IDs that no `tool_use` block of the stored messages carries, and `unadmitted_tool_ids` the `tool_use` IDs that are not admitted, so the set is rebuilt exactly; before, the whole set was written in hash order on every save. A model call's receipt names its assistant message by `content_record` instead of repeating its content, and a completed turn's output names the last assistant message by `final_record` when its text blocks are the final message; both records are the ones the history pages reference, so a reply is stored once instead of three times. `ClaudeCheckpointFormat::hydrate_noting`, the policy's continuation, step replay, admission replay and acquisition rebuild version 1 values, so everything that reads a checkpoint as a value is unchanged; version 1 and 2 checkpoints and cursors (version 1 cursors with `pending_base`) still load, forks, compactions, developer-notice checkpoints, subagent child states and exports stay version 1, and older binaries reject version 3.
- KeyValueStore keeps a state's head at `{prefix}state/{state_id}` and its content-addressed records at `{prefix}record/{state_id length}/{state_id}/{key}`, written before the head swap and never deleted, so a failed replace leaves only unreferenced records. Versions are `fence.revision.owner` strings the adapter chooses and hosts store and compare verbatim; a failed swap rereads the head to report Fenced or Conflict, and acquisition retries until it installs the next fence. compare_and_swap must be linearizable per key, so eventually consistent stores such as Cloudflare KV cannot back it.
- runtime/durability session drivers: SessionStore::session and resume and DurableSession::open, open_shared, open_shared_described and open_sibling acquire ownership and persist the record before returning, fencing earlier owners. prepare_session, prepare_resume and prepare_shared_described return a driver without writing, and its first command acquires once through acquire_with with the prepared record merged, which JSONL commits with one full disk sync, so use them only where construction consumes the driver at once. `acquire_agent_with_initial_checkpoint` commits the backend's initial checkpoint in that acquisition when the state has no record, checkpoint or operations and returns `InitialAcquisition::Existing` otherwise, and `seeded_child_journal` with `acquire_agent_with_initial_checkpoint_and_journal` folds the subagent tree acquisition into the same synced batch only when the store batches companion acquisition, never on WASM. NotCommitted acquisition failures may be retried; other failures poison the driver. Startup durability is bounded by full disk syncs, about 5 ms each with F_FULLFSYNC on APFS, so measure entries, syncs and latency when changing acquisition paths.
- `DurableOwner::commit_writes` applies one operation's `OwnerWrite` values in order with one commit and one revision; nothing commits when any write fails, and a BeginStep for an existing step returns its Interrupted or Replay outcome without writing (three commits per tool step took 5.9 ms instead of 18.6 ms). `DurableSession::stage` queues a `SessionWrite` onto the driver's next commit of any kind, including a live agent's owner commits. NotCommitted keeps it queued; any other error peeks the state: the payload at the expected revision means the commit landed, the previous revision is retried once with the same revision-conditional commit, and anything else poisons the driver. `append` commits staged writes at once, `commit_checkpoint` commits a standalone checkpoint with its write, and after either fails with NotCommitted flush with an empty append, because retrying the same write duplicates its events. `MetadataWrite` is a data-only compare-and-set that cannot change identity fields. `DurableOwner::abandon_stale_kinds` registers maintenance kinds, Codex standalone_compaction and Claude compact and session_end, that the driver cancels when unclaimed at the head of the pending queue: once when they are registered, which each backend does right after its owner acquires the session and before any attempt of its own, and again before each admission, attempt and standalone checkpoint; prompt turns are never abandoned.
- A durable state's head keeps its pending operations, the terminal receipts accepted after its last sealed one and references to sealed receipt pages instead of every receipt. Before each commit of a driver without a terminal receipt limit, `JournalState::seal_receipts` seals each run of 16 terminal receipts that no pending operation precedes into an immutable content-addressed page record, and each 16 page references of one level into a page of the next, so the head holds fewer than 16 unsealed terminal receipts and fewer than 16 references per level; a limit keeps its retained receipts in the head and seals nothing. Every receipt stays available: the driver's acquisition, `SessionStore` reads, `SessionReader::state` and `CheckpointBranch` load the pages, one record read per level, before they use the operations, so idempotent admission, replay and rewind see all of them, and accepting an operation before they are loaded fails. A head that references pages is state format 5: format 4 heads load and are sealed on their next commit, a head with nothing sealed is still written as format 4, and older binaries reject format 5. Tools that read operations from a stored head follow `sealed.levels` to the page records, as the Worker's measure-faults does.

- [Principles for fast Tokio applications](https://dial9-rs.github.io/blog/principles-for-fast-tokio-applications/)
- Write lock-free code: no Mutex, RwLock or Condvar from std, Tokio, futures or parking_lot anywhere in the workspace. Use the nanocode-sync primitives: own mutable state in one task and talk to it over channels or an Actor, publish shared state as an Atom or ArcSwap value changed copy-on-write with side effects performed after the change commits, use Slot, Signal, atomics and OnceLock for take-once values and flags, Ordered to publish effects in commit order, and Sequencer or Owned only where a protocol requires one caller at a time across awaits.
- nanocode-sync semantics: `Atom::update` clones the value, applies the change and retries the compare-and-swap, so a change may run more than once and must be free of side effects; `try_update` skips the store on None and `modify` on an error. `Signal` fires once for current and future waiters, `Slot` put and take swap atomically and never read in place: `is_empty` reads an occupancy count kept beside the value, because loading the value for the check made a concurrent take or put find it shared and drop it. `Ordered` delivers values in ticket order, so every ticket must be published exactly once. `Inbox` pushes by compare-and-swap and drains in push order. `SingleFlight` runs one future per concurrent burst, and a cancelled leader hands the flight to the next caller. `Sequencer` admits one `Turn` at a time in arrival order, and a cancelled `enter` passes an admission it already received on. `Owned` moves its value to the admitted caller as `Held` or `Leased` and back before the next turn. `Actor` runs jobs on its own task in call order and cancels a job whose caller drops its future; it needs a Tokio runtime natively or an installed platform host on WASM.

The revision stays recorded after the completion settles, so a restore can tell a child whose mark never reached the journal: when a process exits after the cancel but before that write, the cancelled turn is already terminal and nothing replays it, so restore asks the store (`ChildJournalStore::cancelled_turns`, through `SubagentStore::cancelled_turns`) which recorded host contexts of running root children without a mark name a root operation recorded as cancelled, and gives those children the revision their resumed work settles at, journaled with the resume attempts. Delivery is at least once.
- A notice turn that fails with a definite error (`BackendFailure::retryable` false, such as a 403 without `x-should-retry: true`, a 400 or a replayed failure) parks its completion as a cancelled notice turn does: journaled as parked with its attempt, left out of `SubagentActivity::pending_completions` and `deliver_completions`, and steered into the next prompt the root accepts that is not a completion notice, also after a restart, under the next attempt's request ID.
