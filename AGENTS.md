- Bash commands start in a shell that is already running (`integrations/process/src/warm.rs`, macOS and Linux): Claude's `Bash` (`run_bash`) and an `exec_command` that runs bash without a PTY (the default shell on most Linux machines, or a model-provided bash) take an idle `bash -c LOADER` (or `-lc`) started earlier with the same shell, login flag, workdir and environment, write the command to its stdin and use its pipes, where each used to start a new bash. The loader closes every inherited descriptor above 2, prints a NUL once it is ready, reads the session variables (`SessionEnvironment::VARIABLES`, exported before the command, so sessions share processes) and then the command, each up to a NUL, takes `/dev/null` as stdin, resets `SECONDS`, sets `$_` to `$BASH` and `eval`s the command from `BASH_EXECUTION_STRING`, so `$0`, `$$`, the environment, the cwd, exit codes, traps, timeouts and process-group kills are a fresh `bash -c`'s; what differs is that syntax errors read `bash: eval: line N:` (as in Claude Code, which also `eval`s commands) and exit 1 under bash 3.2, and `$_` names the shell rather than an inherited `_`. Each process runs one command. A command over 4 KiB (bash reads a pipe a byte at a time, 0.4 µs per byte on an M1 Max, which passes a bash start's 4-8 ms near 12 KB), or with a NUL, starts its own shell, as do commands for which no idle process is left; an idle process whose startup files (for login shells `/etc/profile`, `~/.bash_profile`, `~/.profile`, `~/.bashrc` and the like, plus `BASH_ENV`; `/etc/paths` on macOS) or workdir changed, or that died, is discarded. Each pool (one per shell, login flag, workdir and environment) keeps as many idle processes as it last needed: one after its first command, one more whenever it hands out a process that had not finished starting, one fewer when it hands out a ready one while another ready one waits, refilled one at a time on a blocking thread after each take; all pools together keep at most one idle process per CPU and evict the least recently used pool's. An idle process exits when its stdin closes, so they go with the process that started them. On 2026-10-27 in nanocode-ts's `bench/hands.mjs` (WASM brain, native hand, medians of 10 turns, load average about 20 from other builds on an M1 Max with nix-darwin's bash) a cell with one `Bash` call took 6.0 ms instead of 12.4 and 50 sequential calls 137 ms instead of 333, and 50 at once took 76-100 ms against 70-91 (the same within that load: the build with the pool switched off measured 83-95); in a Debian bullseye arm64 container (bash 5.1, OrbStack) one call took 5.3 ms instead of 7.1, 50 sequential `Bash` calls 34 ms instead of 46, 50 sequential `exec_command`s (bash -lc) 39 ms instead of 94 and 50 at once the same (23 ms). Starting it exposed a stall that older builds have too: on macOS, std creates a child's pipes with `pipe` and then sets close-on-exec, so a child spawned at that moment on another thread inherits the write end of another command's output pipe, and a child that lives long (a warm bash, or a zsh shell server below) keeps that command's output open: its `Bash` or `exec_command` call never saw EOF and its cell came back only at its yield, after 11 s, in about one of 20 turns of 100 mixed `Bash` and `exec_command` calls at once, with the build before this too. The warm loader closes every inherited descriptor above 2, and the zsh shell server's bootstrap now first closes every inherited pipe and socket above 2 (zsh's own descriptors, 10 and 11, are a terminal and `/dev/null`); 140 turns of those bursts after the change showed no stall.
- `ShellSessions` runs an `exec_command` of the default shell, when that is zsh and the call asks for neither a PTY nor a `shell`, in a forked copy of a long-lived zsh instead of a shell started for it (`integrations/process/src/server.rs`, macOS and Linux). A dispatcher per login flag starts up to one server per CPU (`zsh -lc` or `-c` with the first command's environment and workdir; the startup files are read once) and hands each server at most 2 unanswered starts (`DEPTH`), so a server's status queries never wait behind a backlog of forks and a burst spreads over servers as they start: 2,048 commands at once took 0.73 to 0.96 s in a release build instead of 5.6 to 8.9 s with a queue per server. The server forks one subshell per command as a background job, so each command is its own process group; the subshell opens its own stdout and stderr (FIFOs in a `0700` `$TMPDIR/nanocode-shell-<pid>-<random>` directory, reused once both reached EOF), takes `/dev/null` as stdin, `cd`s to the workdir (to `$PWD` when that is the same directory, as a new shell keeps it, else `-P`), exports the command's environment where it differs from the server's (every secret, always; a read-only or non-identifier name makes the command start its own shell; an environment equal to the server's, in the same order, is not compared name by name), unsets what the command lacks, sets `OLDPWD`, reseeds `RANDOM` and resets `SECONDS`, and sources the command from a file named `zsh` with that prelude on its first line, so `$0`, `$LINENO`, `return` and messages such as `zsh:3: command not found: x` read as in `zsh -c`. The server runs with `bg_nice` off, so commands are not niced (zsh's default ran every served command at nice 5), and `notify` on, so zsh drops each job once it reaped it rather than at a prompt or a `wait` (with it off, a non-interactive zsh that started 1,100 background jobs and waited for none aborted at the 998th); the prelude restores both for the command. The caller gets the command once the server names its PID (a command the server never forked starts its own shell), and the Hand learns its exit from kqueue `NOTE_EXIT` (a pidfd on Linux). The status comes from the command itself: the subshell's EXIT trap prints it on a close-on-exec copy of the server's output (zsh/system's `sysopen`, unloaded again unless a startup file loaded it, so programs the command runs see no extra descriptor), which the Hand reads before it takes an exit; the server's `wait` gives it only for a command that ended without the trap (exec, a signal, a fatal shell error, or an EXIT trap of its own), and the PIDs that reported ride along with the next request in a `c` line so zsh forgets their statuses. That is so a server's death costs no command: zsh exits whenever a fork of a non-interactive shell fails (`fatal:` in exec.c, `exit(1)` after "fork failed", as at the user's process limit, and also for "pipe failed" and a full job table). The dispatcher hears of it at once, the server's last error (its `log`) is logged, and the commands it was running go on and report their status; only one that ends without the trap fails with "failed to wait for shell command: the shell server stopped". With `ulimit -u` 390 above the user's process count, 4,000 calls of `sleep 0.2; echo $RANDOM` 200 at a time through tempoxyz/pyramid's `exec_bench` lost the status of 930 to 3,800 calls before and 2 to 3 after (commands whose own fork failed, so their shell exited without its trap); the previous build also panicked re-awaiting the server watcher's oneshot (`called after complete`, 27 times in those runs), which left the dispatcher a dead server and hung one run. The Hand then stops the command's process group as before, with a single `killpg` when the group is already empty (SIGKILL used to follow a SIGSTOP that found no process); Ctrl-C (`write_stdin` of `\u{3}`), timeouts, cancellation and `terminate_all` signal that group, and `terminate_all` also stops the servers. A command starts its own shell as before when no server is ready yet (a server starts in the background), when its text has `$$`, `${$}`, `$!` or `${!}` (a subshell keeps the server's values), when its workdir is not a directory, when a server reached zsh's job table limit (997 jobs ran at once on zsh 5.9, the 998th aborted the shell), and while startup files print anything (that output then reaches every command, as before); a server that failed to start does not stop later ones, while one whose startup files printed or ended it does until they change. A server is replaced when one of the startup files it read changes (dev, inode, size, mtime and ctime of `/etc/zshenv`, `/etc/zprofile`, `/etc/zlogin`, `.zshenv`, `.zprofile` and `.zlogin` in `$ZDOTDIR` or `~`, and on macOS `/etc/paths` and `/etc/paths.d`; files those source are not tracked) or it dies. Each batch of commands checks those files, on macOS only after a kqueue watch on each file and every directory its path and link targets resolve through saw a change (the stats were 5 to 7% of the Hand's busy samples at 512 calls at once). kqueues are polled with kevent64 and `KEVENT_FLAG_IMMEDIATE`: on an empty queue that takes 0.23 µs, a zero timeout 11.5 µs with either call, and the exit queue is read again only once tokio sees it readable. Differences a command can see: `$ZSH_SUBSHELL` is 1, `$zsh_eval_context` is `cmdarg file`, `getppid()` is the server, startup files run once per server rather than once per command, and `trap` lists the EXIT trap that reports the status. macOS kqueue never reports a FIFO's last writer closing, so once a command exited its output drains read every 10 ms (`REAP_POLL_INTERVAL`) until EOF. The command's file keeps its length and is padded with spaces after the prelude, because truncating it on every command was 5% of the Hand's CPU under load; a command with secrets has its file overwritten with spaces once it exits. Commands that still start their own shell now spawn it on the blocking pool: with 2,048 commands at once about 1,000 of them did, and while `posix_spawn` blocked the async workers 3 to 23 commands per run lost their output, their drains woken on a blocked worker past the 2 s drain grace. `prune` returns before sorting when every session is in a call (all 512 were, on every insert). Sessions are kept in `MAX_SESSIONS` shards (Atom::update copies the whole map, and copying and dropping one map of every session were 5.4% of the Hand's busy samples at 512 calls at once), chunk IDs and `RANDOM` seeds come from splitmix64 seeded once by the OS (a getentropy call each was 1.5 to 2%), sensitive names are matched without allocating, and an output drain keeps its buffer on the heap so spawning it copies no 8 KiB future. On 2026-10-27 on an M1 Max (fish login shell, so `/bin/zsh`; load average 4 to 12; three runs of each, alternating with the previous build), tempoxyz/pyramid's `exec_bench` (`echo` through its Hand's socket) took 1.24 to 1.29 ms p50 one at a time instead of 1.35 to 1.39, ran 3,830 to 3,930 calls/s 64 at a time instead of 3,420 to 3,590 (p95 26 to 27 ms instead of 40 to 43) and 3,800 to 3,950 calls/s 512 at a time instead of 3,430 to 3,480 (p50 126 to 128 ms instead of 134 to 136, p95 142 to 162 ms instead of 229 to 248), and a call cost the Hand and client 0.31 to 0.32, 0.22 and 0.215 ms of CPU instead of 0.37 to 0.39, 0.35 to 0.37 and 0.34 (one, 64 and 512 at a time), with the commands' 1.0 to 1.5 ms unchanged; before the shell server, 512 at a time ran 578 to 955 calls/s at 4.17 to 5.29 ms of command CPU a call. Most of what remains is the fork: a forked zsh subshell that exits and is waited for cost about 0.65 ms of CPU there, 0.5 ms of it in the kernel.

- `Hand::activity()` returns a cloneable `HandActivity` for a host process that must drain before replacing its own binary (its bookkeeping is O(1) per request: the executor, its only writer, pushes each request's work onto a list readers walk without locks, marks it ended when it settles, and rebuilds the list only once ended entries outnumber live ones; it used to republish a snapshot of every running and retained request on every frame, the hottest code in a 64 x 64-call profile): `busy()` is true while the hand has a cell running or yielded, a callback awaiting its result, a request in flight, or a result the brain has not acknowledged (retained for resume), `idle()` resolves once none is left, and `drain()` makes the hand refuse every new `Execute` and `Call` with the reply the brain reads as never dispatched (`NOT_RECEIVED`, so the brain's call is unsent and can be retried elsewhere) while `Wait`s for cells it already admitted, cancels and turn bookkeeping still run, so yielded cells can finish. A task leaves the list when its command exits, however it ended: a command killed from outside leaves `TaskOutput` answering at once with its final status, `TaskStop` saying it is not running and `write_stdin` reporting the exit and then an unknown process. `busy()` and `idle()` cover the same work as the items other than `Task`s (a callback awaiting the brain belongs to the cell or call that made it), so drains that should not wait for background commands keep their meaning; tools report running commands through `Tool::running_tasks()` (default none) and runtimes through `ToolRuntime::running_tasks()` (their workspace tools). `HandActivity` holds the hand's tools weakly, so stopping a hand still ends their commands while a host keeps its activity. A hand reports itself attached on that first frame (the native hand's `HandEvent::Connected` and nanocode-ts's `attached` status), so a hand refused after the upgrade, as browsers are, is never reported attached, and a `SocketTransport` brain no longer leaves its hand unconnected until the first ping 20 s later. `ExecutionEnvironment::local()` (native) is this machine's date and time zone, as a Codex session detects them by default, for hosts that describe another machine's working directory or shell with it, and `SocketTransport::workspace()` is the directory the hand or runner advertised; the `brain` example now describes that directory to both backends (`ExecutionEnvironment::local().working_directory` and `ClaudeEnvironment::working_directory`) when it runs cells remotely, instead of its own working directory and AGENTS.md. Before, on 2026-10-27, Luna passed the brain's checkout as `workdir` to `exec_command` on a hand in `/tmp` and its output named the brain's directory; afterwards the same prompt ran in `/tmp`.
- `Hand::header(name, value)` adds an HTTP header to the WebSocket upgrade request of every dial of a `Hand::connect`ed hand, redials included, next to the bearer token; repeating a name sends each value. A name or value that is not a valid HTTP header, or a name the upgrade or credential owns (`Authorization`, `Host`, `Connection`, `Upgrade`, `Sec-WebSocket-*`), fails `Hand::run` before it dials, as an error and not a panic, and listening hands ignore them. Hosts such as Pact announce their build, protocol generations and capabilities on every dial this way while the socket's first frame stays the catalog. A brain that serves none of the hand's protocols answers the upgrade with 426, which ends the hand with `HandEvent::Rejected { status: 426 }` like a refused credential instead of redialing, so the host updates itself rather than looping.
- `RemoteTransport::recover(context)` lets a durable host finish a remote operation that was in flight when its process restarted, instead of reporting an unknown outcome. A tool call whose durable step began but never completed is admitted as interrupted; Claude and Codex now try to recover it before finalizing it. `exec` and `wait` go to `ToolRuntime::recover_code` and `CodeModeHost::recover`, which answers `Ok(None)` unless a host overrides it, so `LocalCells`, local Code Mode and every other host never run anything. Any other tool goes to the `ToolRecovery` a host sets with `ToolsBuilder::tool_recovery`: `recover(name, context)` returns the call's output or `None`. `RemoteCodeModeHost::recover` (cells) and `RemoteCodeModeHost::recover_call` (a hand tool's `RemoteOperation::Call`, decoded as `call` decodes its reply) build the `RemoteContext` from the call's own `ToolContext`, with the same `session_id`, `turn_id` and `call_id` as the dispatch (for Codex the Responses `call_id` and a turn ID of the form `<session>:<n>`, for Claude the `tool_use` ID and the request ID), and call `RemoteTransport::recover`, whose default is `None`. A transport that keeps a table of dispatched operations, such as Pact's Durable Object beside `RemoteClient::resuming`, returns `Some(future)` resolving to the stored `Reply` result for that key, in the form `ResumedReply` yields (`Ok(None)` when it has none); a host's `ToolRecovery` for its hand tools (Bash, Read, Edit, Write, TaskOutput, TaskStop, `exec_command`, `write_stdin`, `apply_patch`) passes the context to `recover_call`. The result is journaled like any completed call. Recovery never dispatches: it reaches only `recover`, `recover_call` and the host's `ToolRecovery`, never `request`, `call` or a tool's own handler. `None`, `Ok(None)`, an error, a cancelled turn or a reply that does not decode finalize the call as before (`Tool execution interrupted by a host crash; outcome unknown`, status `unknown`, `outcome_unknown` true), and tool hooks do not run for a recovered call. Native Claude runtimes offer only `exec` and `wait` at the top level (`code_only`), so `ToolRecovery` is reached natively by Codex with a direct host and on WASM by both backends. Callbacks into the brain's host tools from a cell that is still running are not restored: `RemoteClient` registers a cell's callbacks only when it dispatches, and the recovered reply's nested calls are published as results, not replayed. Hosts need it because a Durable Object can reset while its hand keeps running and already holds the real result.
- A hand holds the callbacks it awaits from its brain across a reconnect of the same runtime instead of failing them when the socket drops. Each pending `Frame::Callback` keeps its id, origin and reply channel, and when the redialed brain sends `Resume` the hand sends every held callback again as the identical frame, so its id, name, input and context (the brain's authorization of the origin) are unchanged and a brain that already ran it before the drop can deduplicate by callback id; a `CallbackResult` for a held id reaches the waiting cell as usual. Callbacks a cell makes while disconnected are held too. A callback that no `Resume` reaches within `ExecutorOptions::callback_hold` (`Hand::callback_hold(duration)`, 60 s by default) fails with the dropped-connection error as before, and a hand that is not resumable or is reset (a new runtime) fails them at once. `DetachedUpdate` and `DetachedComplete` frames for yielded cells used to be discarded while disconnected; the hand now keeps up to 1,024 of them (the oldest dropped first) and sends them in order after the `Resume`, before any later frame.
- Hosts that serve a hand's socket with `serve_queue` or route a call into a shared provider session get small accessors instead of their own adapters: `RemoteCatalog::publishes(name)` says whether a catalog publishes a tool, `RemoteCatalog::frame_limit(limit)` is the hand's `max_frame_bytes` capped at the host's own limit (the largest frame either side writes), `Settlement::outcome()` is the receipt a `CommandQueue` stores for a settlement in the attachment protocol's outcome form (`{"status":"completed","output":…}` or `{"status":"unavailable","message":…}`; none for `Unknown`), and `ToolContext::with_session_id(id)` is the same call's context under another session ID, as tempoxyz/pyramid's Hand sends every `computer` step to one nanocode-cua session.
- `nanocode_code_mode::remote::MessageLink::new(stream, writer, max_frame_bytes, resumes)` is a `RemoteLink` over a message connection, such as a server's WebSocket, for hosts that accept a hand's socket themselves and serve it with `serve_queue` or a `RemoteClient`: `stream` yields the peer's text messages (an error fails the link with its text; its end is `PEER_CLOSED`) and is read by one caller at a time through `nanocode_sync::Owned`, `writer` is a `MessageWriter<M>` taking each frame as any `M: From<String>`, and `close` writes nothing, so the host closes with a reason of its own. `MessageWriter::new(sink)` returns the writer and the future that owns the sink and writes every message in order (`MessageWriter::spawn(sink)` spawns it natively); clones of the writer share it, `send(message)` resolves once the message is written and flushed, and the sink closes when the last clone is dropped, so the link, its heartbeat and the host's own final Close share one sink without a lock. Both used to take the sink as `Arc<tokio::sync::Mutex<Si>>`, which made every host hold a Mutex and made pings and frames wait for each other's writes. tempoxyz/pyramid's broker maps axum's `Message` into it instead of implementing the link. `nanocode_chatgpt_extension::Connection::relay(socket, idle, title)` serves browser steps for a host process on a Unix socket of newline-delimited JSON (`hello`, then `call` answered by `result`, and `turn_ended`), naming a session's tab group after the step input field `title`, ending turns idle for `idle`, reconnecting while the connection is live and then waiting for the browser as `finish`; Pyramid's Hand used to carry this loop itself. `remote::websocket(stream, writer, max_frame_bytes, resumes, classify, ping, (interval, timeout))` (native) builds one over a WebSocket library's own messages, which `classify` maps to `SocketMessage`: it answers pings with the pong `classify` gives, fails on a read error or another message and ends on close, and returns a heartbeat future that writes `ping()` every `interval` and resolves with `heartbeat lost` after `timeout` without a pong or `socket write failed`, for `serve_queue`'s `failed`; Pyramid's broker passes axum's `Message` through it instead of tracking pongs itself.
- `nanocode_code_mode::remote::read_catalog(first, timeout, max_frame_bytes)` reads a hand's catalog from the first frame of a socket a host accepted itself (`first` resolves to `None` when the connection ended or failed first, `Some(None)` for a frame that is not text, `Some(Some(text))` otherwise) and fails with `CatalogError::NoCatalog` (none within `timeout`: transient, the hand should reconnect), `Outdated` (not text, or JSON without `definitions`, as `RunnerPool` tells protocols apart) or `Invalid` (a catalog that does not decode). `admit_runtime(previous, connected_before, live, advertised)` is the pure decision whether the runtime a catalog advertises takes the hand: `Fence` for a retired runtime (another runtime took the hand after it), even while its successor's socket is open; `Wait` while another runtime's socket still counts as open, since a host can't tell a live competitor from a dead or sleeping process's socket, so the new runtime reconnects rather than stopping for good; `Retry` for the same runtime while its previous socket on this host is still open; else `Take { replaces }`, where `replaces` retires the previous runtime and forgets its undelivered operations. tempoxyz/pyramid's broker keeps its storage, logging and close codes around both.
- `RemoteContext::new(session_id, call_id, turn_id)` is the context of a call a host queued without a model session, such as a row of tempoxyz/pyramid's `hand_commands` served with `serve_queue`: no model, history, instruction revision or host context, and an output token budget of JavaScript's largest safe integer, the attachment protocol's "no budget beyond the tool's own".
- Streamable HTTP MCP runs on both targets. `McpServer::max_response_bytes(bytes)` bounds what one response may make the client read: a JSON body, an error body, each SSE event and the whole of a request's SSE response stream (the standalone stream only per event, since its total grows for as long as it is open); past it the call fails with a transport error whose effect is unknown, as tempoxyz/pyramid's own client failed past 4 MiB. Without it nothing is bounded but SSE events at 16 MiB, as before. `McpServer::standalone_stream(false)` opens no standalone GET stream, which a client making one call per session, as Pyramid's integrations do, never reads. `McpServer::reuse_connections(true)` keeps idle connections in the client's pool: the client otherwise opens a connection for each request (initialize, initialized, tools/list, the call and the session's DELETE), so 20 one-call sessions against a mock server opened 101 connections without it and 21 with it, each one a TCP and TLS handshake against a real server; it stays off by default, since a request on a connection the server closed while it idled may be one whose outcome is unknown. Both reach the transport as `streamable_http::HttpOptions` (`spawn_with_options`, `spawn_with_sender_options`; `spawn` and `spawn_with_sender` keep the defaults). Checked on 2026-10-26 against a mock server: with a 1 MiB cap a 100 KB result passed and a 5 MB one failed as unknown, and without the stream the server saw no GET. `streamable_http::spawn_with_sender(url, sender, headers, auth, outgoing, inbound)` drives the same protocol code as the native reqwest `spawn` (session and protocol-version headers, JSON and SSE replies, SSE resumption, 404 re-initialization, bearer tokens and the `BearerSource` 401 retry) over any `nanocode_http::layer::Sender`, with `nanocode_platform::{spawn_local, sleep, timeout}` for its background work on WASM. On WASM `nanocode::tools::mcp` is `nanocode_mcp_tools` for HTTP servers only: `McpBuilder::http_sender` supplies the sender, and stdio servers, OAuth, reloads and the deferred tool-search provider stay native. `PreparedMcpTool` implements `Tool`, so a host awaits `Mcp::prepared_servers` and registers each tool with `ToolsBuilder::tool` on either target, with the catalog's names, schemas and result conversion; gakonst/nanocode-ts does so for its `mcp_servers`.
- MCP transport failures are typed: `nanocode_mcp::Error::Transport` carries a `TransportError` whose `is_unsent()` says the request certainly never reached the server (a connect or request-builder error, a body or parameters that failed to encode, an OAuth or `BearerSource` token that could not be obtained, or a request made after its session closed, such as once a stdio server exited, which `Session` refuses before queueing it), and whose `status()` is the HTTP status of a non-2xx response that failed it: a 4xx without a JSON-RPC error body (401 and 403 challenges included, and 404 when an expired session could not be reopened, so the request was not resent) or any 5xx, whose JSON-RPC error body, if any, stays in the message because a server that failed may have acted. A 4xx JSON-RPC error, such as a 402 payment request, still arrives as `Error::Rpc`, with the reply's status in `RpcError::status`; one sent with a 2xx or over SSE has none. Anything else, such as a stream that broke after a 2xx, has neither and its outcome is unknown, as has `Error::Closed`, which now means the session closed after the request was queued; a request refused by a closed session used to be `Error::Closed` too. `message()` and `Display` keep the earlier text. Hosts that record calls before sending, such as Pyramid, use these to report a call as not done instead of fencing it as unknown.
- `nanocode_mcp_tools::tool_output(result, server, tool)` is the conversion `PreparedMcpTool` uses from a `CallToolResult` to the model's `ToolOutput`, public so hosts that call MCP tools themselves, such as tempoxyz/pyramid's integrations, show results the same way and leave image limits to the runtime's image preparation (unsupported, undecodable or oversized images become placeholders before a model request). A result with image, audio or encrypted content is shown as that content even when it also has `structuredContent`, which stays the structured result; before, `structuredContent` won and the images were dropped. `value_output(result, server, tool)` does the same for a result held as JSON and shows a value that is no `CallToolResult` as JSON.
- `McpCallError::effect` says what is known of a failed MCP tool call's effects, so hosts that record calls before sending them, such as tempoxyz/pyramid, don't each classify the error: `Refused(message)` when the server or the host refused it before anything ran (a JSON-RPC error carried by a 4xx reply or whose code says the request was rejected before it ran: parse error, invalid request, method not found, invalid params or -32042 payment required, with its message; a 4xx other than 401 without one, as `HTTP <status>`; or, as `Refused(None)`, an `OAuthRuntime` refresh that failed before the request), `Unsent` when the request never reached the server (`TransportError::is_unsent`, a bearer source that could not give a token included, since the host that implements it knows why), `Unauthorized` for a 401 the transport could not resolve with a fresh token, and `Unknown` for anything that may have run: any other JSON-RPC error, such as an internal or implementation-defined error a server answers with a 2xx or at the end of an SSE stream after its handler started, a 5xx, a broken stream, a timeout or a payment failure. Every JSON-RPC error used to count as refused.
- `nanocode_mcp_tools::stdio::spawn(command, outgoing, inbound)` runs a newline-delimited JSON-RPC MCP server as a child process for any `nanocode_mcp::Session`: it pipes the child's stdin and stdout, starts it in its own process group with kill-on-drop, returns its stderr for the caller to drain or log, and stops the process group when the session's last handle is dropped. Hosts that drive one MCP stdio server themselves, such as Pyramid's Hand for its computer-use provider, use it with `Session::new` instead of a JSON-RPC loop of their own.
- MCP OAuth serves web backends as well as the native loopback login. `nanocode_mcp_http::oauth::discover_server` discovers an MCP server's authorization (an unauthenticated `initialize` POST first, because its 401 challenge carries the scopes to request and some servers answer a GET with 404 or 405, then the well-known probes) and `discover_issuer` an authorization server without an MCP server, each returning an `OAuthServer` with its metadata, resource indicator (none for an issuer) and scopes. `select_scopes` follows the MCP spec's order: the challenge's scopes, else the protected resource's, else none, so the scope parameter is omitted and the authorization server applies its defaults, plus `offline_access` where offered and at least one scope is requested (alone it would replace the server's default scopes; a host that adds scopes of its own afterwards, such as Pyramid's catalog scopes, calls `AuthorizationMetadata::add_offline_access` again); it used to request the union of the first two. `register_web_client` registers a confidential client (RFC 7591) with the first of `client_secret_basic`, `client_secret_post` and `none` the server supports, and honors the method the server assigns. `WebLogin::start` takes the host's redirect URI, scopes, extra authorization parameters and a state prefix and returns the authorization URL and a serializable `PendingWebLogin` the host keeps under its `state`; `PendingWebLogin::complete` checks the callback's state, client and `iss` (RFC 9207) and exchanges the code. The native `begin_login` runs on the same two steps. An empty resource omits the `resource` parameter from authorization and token requests. `ClientAuthentication::with_method` and `method` map RFC 7591 method names, `revocation_request` and `revoke_token` revoke a token (RFC 7009), and `token_endpoint_request` is public for refreshes a host schedules itself. `parse_token_response` accepts a missing `token_type`, a string `expires_in`, Slack's `authed_user.scope` when `scope` is absent, and a 200 that carries an OAuth `error` (GitHub); `invalid_grant`, `invalid_client`, `unauthorized_client`, GitHub's `bad_refresh_token` and a 401 without an error body are `TokenError::Rejected`, meaning sign in again. `McpOAuthCredentials::client` keeps a confidential client's secret and method, so `OAuthRuntime` refreshes such clients, and the native login stores the client it registered. tempoxyz/pyramid runs its integrations' sign-in and revocation on these, and their refreshes on `OAuthRuntime` over its own `McpOAuthStore` (sealed per-member token sets in Postgres, an advisory lock across backends). `oauth::http_client(user_agent, https_only, timeout)` builds the `HttpClient` a web backend passes these functions, with the rustls provider installed and no redirects, so no token follows one to another host.
- Web backends that run MCP OAuth themselves get its generic pieces: `OAuthServer::issuer` (the metadata's issuer without a trailing slash, which keys registered clients and token sets) and `OAuthServer::endpoints` (authorization, token, and registration and revocation when offered, for hosts that vet them, such as HTTPS only), `revoke_sign_in(http, endpoint, client, access_token, refresh_token)`, which revokes the refresh token when there is one, since that ends the grant, else the access token, and `PreparedMcpTool::listed`, the tool as `tools/list` gives it (remote name, description, input schema, readOnlyHint). `McpOAuthStore::authorization_required` is an `async fn` like the trait's other methods. tempoxyz/pyramid's integrations use them instead of their own copies.
- `OAuthRuntime` serves stored sign-ins without rediscovery and APIs other than MCP servers. `McpOAuthCredentials::token_endpoint` names the token endpoint the sign-in found, and refreshes go there without discovering the server's authorization again (and without checking its issuer against current metadata); `resource` sets the resource indicator refreshes send instead of the server URL, empty for none, as for an authorization server found by `discover_issuer`. Refreshes keep both. `OAuthRuntime::stored(server_name, server_url, http, store, credentials)` builds a runtime for such credentials, whose `server_url` only names it to the store, and `transport_from_credentials` uses it for them; `access_token` and the now public `refresh_after_rejection` give a host's own API calls the same refresh as MCP requests. `with_access_token(call, refused)` wraps one such call: it calls with the current token and, when `refused` says the API refused it, refreshes after the rejection and calls once more, calling `refused_after_refresh` when the refreshed token is refused too; tempoxyz/pyramid serves its Google Workspace tools through it. `McpOAuthStore::authorization_required` (a no-op by default) hears when only authorizing again helps: the authorization server rejected the refresh token (`TokenError::Rejected`), none is stored, or a server refused the token just refreshed after its rejection (`refused_after_refresh`, which the Streamable HTTP transport calls); transient failures don't call it, and a refresh that fails transiently before the token expires keeps using it. Refreshes join in process per store as well as server name and URL, since a host with a store per user, such as Pyramid, reuses server names; a store is its instance unless `McpOAuthStore::refresh_key` names it, which hosts that build a store per call (Pyramid) return, such as the member's ID, so their refreshes join too.
- Hosts that keep their own per-user credentials, such as Pyramid with each member's tokens in Postgres, authenticate Streamable HTTP MCP with `HttpAuth::Source` (`McpServer::bearer_source`): the transport asks the `BearerSource` for a token before every request, and calls `rejected(token)` with every token a server refuses with a 401 challenge. The first refusal of a request is retried once with the token `rejected` returns when it differs; a refusal of that retry is reported to `rejected` too and its result ignored, so the source can tell a refreshed token that is still refused (the sign-in is gone) from an expired one. A `token` error fails the request as unsent. `Mcp::prepared_servers` waits for discovery and gives each configured server its callable tools or its error (a server still pending after the discovery timeout, twice the longest startup timeout unless `McpBuilder::discovery_timeout` sets it, fails as timed out), so a host can offer the servers that answered and say which did not. `PreparedMcpTool::call` sends one `tools/call` within the tool timeout and returns the `CallToolResult` or a typed `McpCallError` (`Session` keeps the `nanocode_mcp::Error` with its unsent flag and status, `Timeout` means the outcome is unknown), so hosts that record calls before sending fence only unknown outcomes; `read_only()` is the tool's readOnlyHint.
- `nanocode_process::set_command_environment(variables)` sets variables that every command in the process gets, such as an app's `GH_TOKEN`: `exec_command` sessions, Claude's foreground `Bash` and hands, after the process environment and before a call's own variables, for hosts whose users connect accounts once and expect every session's commands to use them. - `nanocode::http::origin` (`nanocode_http::layer::origin`) tells a host transport which work a model request continues. While an agent's model call is polled, `origin::current()` returns its opaque origin: the agent's host context, or for a root without one the durable operation of its turn, which is the prompt's request ID, a subagent completion turn's `subagent-completion:` ID or a compaction's operation ID, the same value its tool calls carry in `ToolContext::host_context`. - `FunctionTool` in runtime/tool-host is the adapter for tools a host declares at run time, such as a JavaScript host's: each has a name, description and JSON Schema parameters, and its calls run through an `Arc<dyn FunctionHandler>` whose async `call` receives the tool name, the decoded JSON arguments and the `ToolContext`. - Remote Code Mode links write in batches, encode each request once and decode frames without buffering. `MessageWriter` drains every queued write before its one flush, and the hand's writer task writes every queued frame under one deadline (`write_all`), so replies and requests that queue together share a syscall. `RemoteClient` keeps the text it encodes to check a request against the frame limit and passes it to `RemoteLink::send_encoded`, whose default calls `send` (which encodes again) and which `MessageLink` and the native `SocketLink` use as is; requests used to be serialized twice, which for an Execute includes its source and brain tool definitions. A resumable client acknowledges replies in the next batch it sends, and only after `ACK_DELAY` (10 ms) when nothing else goes out, instead of writing an `Ack` for every batch it reads: in a loop of sequential calls the next request follows a reply within tens of microseconds. `RemoteFrame` deserializes through `remote/frame.rs`: it reads the `type` key first, as every encoder writes it, and deserializes the rest of the object straight into the variant (a frame whose `type` comes later takes a slower path through `Value`); serde's derive for internally tagged enums buffered every frame into `Content` first, 10-16% of a call's CPU. The hand publishes the work `HandActivity::items()` lists at most every 10 ms (`WORK_PUBLISH_DELAY`) instead of on every request and reply, because an `Atom` store makes the writer pay the read debts of every thread that used arc-swap (about 1-2 µs, 10% of a call's CPU at 16 concurrent calls); a call finishing still shows at once through its `ended` flag. Shared admissions of calls outside a cell (no origin) count on an atomic in the admission gate unless an exclusive call holds or waits for it (`CLOSER`), instead of cloning and swapping the gate state twice per call; the gate stress test with direct calls mixed in (output/hand-wiring `gate2`, 1,800 rounds with and without cancellations) found no violation or stuck gate. Native sockets read with a 16 KiB buffer (`READ_BUFFER_BYTES`), because tungstenite zero-fills its whole read buffer (128 KiB by default) before every read, which cost 7% of a call's CPU; 16 KiB measured as fast as 4 KiB for small frames and faster than 4 and 128 KiB for 64 KiB ones. A resumable hand encodes a retained reply once when its live form is the same. Measured with output/hand-wiring's `rtt` (a `RemoteClient` over `MessageLink` and a `Hand::connect` hand with a noop tool in one process on loopback, interleaved A/B on a shared laptop, 2026-10-26): a sequential Call went from p50 65 to 45 µs and 78 to 50 µs of CPU, 16 concurrent callers from 59.9k to 83.1k calls/s (53 to 39 µs of CPU each), a 64 KiB Call from 252 to 186 µs, a callback round trip from 481 to 392 µs; the Worker demo's measure-hand-load (4 sessions of 40 pong turns, 20 ms polls) went from 86 to 105 turns/s and 12.4 to 10.6 ms of workerd CPU per turn with the durability changes. After 2 ms idle a Call takes about 140 µs here, the same with a single tokio thread for both ends, so idle starts pay cache and clock warm-up rather than thread hand-offs, and shrink only with the work per call.
- `nanocode_code_mode::remote::RemoteClient` owns the brain side of the remote Code Mode protocol on every target: pending replies, brain and hand callbacks, detached cells and their turn generations, cancellation, operation deadlines and unknown outcomes after a disconnect. The pending replies belong to the driver alone: a caller sends its reply channel in the same channel item as its frame, so no reply can arrive before its waiter, and a dropped caller sends a forget; `RemoteClient::calls(Vec<(id, operation)>)` sends a batch of Calls under caller-chosen IDs as one item, so the link gets them in one `send`. The map used to be an `Atom<HashMap>` that every request copied on insert and on removal, O(n) per request with n in flight: through a loopback hand, 64 sessions running cells on the hand with 64 nested calls each went from 12,091 to 51,913 calls/s. `RemoteClient::new` runs it over any `RemoteLink`, which only sends and receives frame batches and closes the connection, and returns a driver future the host spawns. `SocketTransport` in integrations/tool-runtime is the native WebSocket link with dialing, accepting, heartbeats, liveness and close frames; WASM hosts implement `RemoteLink` over their own sockets. Only frames whose effect the brain must have recorded first are `RemoteDelivery::Durable`, so a host makes its state durable before sending a batch that contains one: `Execute` and `Cancel` requests and brain callback results. Turn bookkeeping (`BeginTurn`, `DetachTurn`, `SettlePreempt`, `EndTurn`), `Wait`, `CancelTurn`, `Preempt`, `CancelCall`, relayed hand calls and their results are `Immediate`: none starts work on the hand, and a brain that loses its state after sending one reports the cells it finds gone as unknown outcomes rather than replaying them. On a deployed Cloudflare Durable Object (nanocode-ts syncs storage before every durable send, about 20-35 ms each) this took two confirmation waits out of every Code Mode turn: a mock-model turn with one cell on a hand went from p50 317 to 280 ms inside the object, and to 102 ms when nanocode-ts also stops syncing before model requests, which have no side effect to protect (2026-10-26). `RemoteFrame::dispatches` marks the requests that start or continue work on the peer (Execute, Wait and Call), so a host can refuse to send them, for example once a turn's cancellation is requested, without decoding frames itself. `RemoteCatalog::decode` reads the catalog a hand or runner publishes as its first frame, with its tool definitions and advertised name, and rejects any other first frame with `NO_CATALOG`; the native `SocketTransport` and WASM hosts use it alike, so a host that stores the catalog across hibernation keeps it as opaque text. `RemoteLink::changed` runs after each received batch and finished callback, `RemoteActivity::busy` reports running callbacks and detached cells for host idle checks, and `RemoteActivity::is_alive` reports whether its client still exists. A link that wrote none of a batch, such as a host refusing it for a revoked hand or a cancelled turn, fails `send` with `CodeModeHostError::unsent`; when the connection ends, operations whose request no link accepted, or a link refused that way, report that they were not dispatched, and only requests a link may have written report unknown outcomes. A link that refuses only some request frames of a batch, such as a host that shares one link among turns and stops one turn's dispatches, writes the other frames and fails `send` with `CodeModeHostError::refused(reason, ids)`: the client counts the rest of the batch as written, fails only those requests' operations as not dispatched and keeps the link and its other operations running; refusing an ID that is not a request of the batch fails the link like any other send error. `RemoteLink::max_frame_bytes` is the largest frame both ends accept: `SocketTransport` and the WASM package's link take the smaller of their own policy and the `max_frame_bytes` a hand or runner publishes in its catalog, and every request carries it, so the hand learns the brain's limit. No side writes a larger frame: the brain fails an oversized request as not dispatched and replaces an oversized callback result with the limit error; a hand replaces the inputs and outputs of an oversized result's nested calls, and then its output, with the limit error while keeping its cell, sends oversized nested-call updates without their payloads and fails an oversized cross-hand call without dispatching it. Before this, one 1.5 MB `text()` or cross-hand `Write` on a Worker hand closed the connection and failed every pending call with an unknown outcome. Execute, Wait and Call deadlines add the operation's requested `yield_time_ms` (a Call's from its input, such as a `write_stdin` poll of up to 300 s) to the operation timeout, because a model-chosen yield longer than the host's timeout otherwise expired the deadline and cancelled the turn's cells or reported the call's outcome unknown. Each client starts its request IDs at a random offset below 2^52, so when a host hands a connection to a new client, as the Worker does for a runtime reopened after a failure, a late reply to the previous client's request cannot reach the new client's request with the same ID. A client knows only the cells its own requests started: when a host hands a live connection to a new client, as the Worker does after a forced Durable Object restart while a hand stays attached, the hand keeps running the previous client's cells, and the new client drops their `DetachedUpdate` and `DetachedComplete` frames, so their completion notices are lost, answers their brain callbacks as unavailable, never answers a callback the previous client was still running, which then waits for the hand's callback deadline (`nanocode hand` sets none), and sends turn controls such as CancelTurn only to hands it has used itself; a Wait on such a cell's ID still reaches the hand through the session's placement. Reporting or cancelling those cells needs the hand to learn that its client changed, or durable records of each session's hands and cells.
- `RemoteOperation::EndTurn { session_id, turn_id, hook_event_name }` tells a remote hand that a turn ended, so its tools release what the turn held: the native hand (`Hand::connect`) calls `Tool::end_turn` on every registered tool, whether or not it runs cells for the session, logs a tool's failure without retrying it, and answers `Ok(None)`; it dispatches nothing, so links that send only tool calls pass it. It is the remote counterpart of the attachment protocol's `EndpointFrame::TurnEnded`. Hosts send it with `RemoteClient::request` once they know a turn ended; tempoxyz/pyramid's broker sends it (`hook_event_name` `Stop`) for turns that ran browser steps, so the Hand's ChatGPT-extension bridge closes their tabs. A hand built before it fails to decode the frame, so send it only to hands built since.
- A hand whose catalog carries a `runtime_id` keeps its work across reconnects when its brain opts in: its catalog says `resumable: true`, and a brain whose `RemoteLink::resumes` returns that runtime ID marks every request `resumable`. `Hand::connect` owns one executor for its whole run, so once a resumable request arrives a dropped socket no longer cancels the session runtimes, their processes or running cells, and a brain that wants a session gone ends it with Cancel. The hand keeps each resumable request's reply until the brain's `Ack`, which a client built with `RemoteClient::new` sends for every batch of replies it receives, and answers requests that finished while it was away on the next connection. A resumable link survives reconnects itself, stays open and passes each later catalog to `RemoteClient`, which sends `Resume` with the requests it wrote and still waits for: the hand resends their replies in full form, because compact replies may name nested-call updates lost with the old socket, leaves running ones to reply when they finish, answers ones it never received with `NOT_RECEIVED` (not dispatched) and forgets the rest; a catalog with another runtime ID fails the client with `HAND_RESTARTED`, so only that runtime's outcomes are unknown. A new client sends an empty `Resume` first, so a hand forgets replies no client waits for, unless it is built with `RemoteClient::resuming`. Cancel and CancelTurn also end a session's in-flight Call requests, which reply with `CALL_CANCELLED` (unknown outcome), because a Call runs one nested tool outside any cell and nothing else could stop it; a process it started may outlive it. A `CancelTurn` with `turn_id` ends only the Calls whose context names that turn and leaves the session's cells alone; without one (the field is omitted on the wire, as before) it cancels the session's turn as it did. A 410 at the WebSocket upgrade rejects a hand's credential for good, like 401 and 403, so a revoked hand stops instead of redialing; `Hand::run` reports it as `HandEvent::Rejected { status }` before returning the error, so hosts match the event instead of the error's text. A policy close (1008) other than revocation or `HAND_REPLACED` fences only the runtime it closed: the hand ends that runtime's sessions, mints a new runtime ID and redials at the longest backoff (5 s), reporting `HandEvent::Disconnected`, because a backend from before a protocol change, or one a deploy rolled back to, closes a newer hand with 1008 and stopping for good stranded every such hand until it was claimed again (6dfd20726 had made any 1008 terminal; tempoxyz/pyramid's PR 219 review rated that its highest risk). On loopback a hand closed with 1008 redialed 5.0 s later under a new runtime ID. Callbacks in flight when the socket drops fail with an unknown outcome, and updates sent while it is down are lost. Brains that do not opt in, the native `SocketTransport` and pool-managed executors among them, see no change: their hands still cancel every session at disconnect. On loopback (a brain whose link outlives sockets and a `nanocode hand` with workspace tools), dropping the socket 1 s into a 3 s `exec_command` Call, a cell whose nested `exec_command` takes 2 s and a background process polled afterwards: before, the hand cancelled every session and the brain failed with `unexpected runner frame` and unknown outcomes; after, the hand reconnected in 100 ms, the Call and the cell returned their real outputs 2.0 s after the drop, and the background process kept running and printed its remaining output.
- A brain that outlives its process, such as a server whose hands reconnect to whichever replica holds their socket, resumes its predecessor's requests with `RemoteClient::resuming(link, timeout, pending)`: its link's `send` sees every Request frame with its ID and the host's `RemoteContext::call_id` before the write, so the host persists that pair there, and after a restart it passes the IDs still unsettled for a link whose `resumes` names the same runtime. The client sends them in its first `Resume` instead of an empty one and returns one `ResumedReply` per ID: the hand's retained reply in full form, the reply when a running request finishes, or `NOT_RECEIVED`, which every reply path surfaces as `CodeModeHostError::unsent`, so a write lost with a dying socket is known not to have run without a separate delivery acknowledgement. Such a client sends no `Ack` itself: the host calls `RemoteClient::ack` with a request's ID once it has durably settled the reply, so a successor resumes every ID whose outcome its predecessor had not recorded and gets the retained reply, never `NOT_RECEIVED` for a request that ran. A link without `resumes` answers each ID with `HAND_RESTARTED` (unknown outcome). A reply's value has its nested calls expanded from the compact field forms, as `request` expands them, while updates are ignored because the full form names none and a successor never saw the updates its predecessor received, so an Execute or Wait reply deserializes as `CodeModeExecution` and a Call reply decodes with `output_from_wire`, as `call`'s value does; before, it was the raw compact value, and on loopback a resumed cell whose nested call returned JSON failed to deserialize with `missing field output`. Only one client may hold a runtime's unsettled IDs, because each `Resume` makes the hand forget replies it does not name. On loopback, a brain dropped 0.7 s into a 2 s Bash Call and a new client built with `resuming` on the hand's reconnect got the Call's real output 2.05 s after it started, and an ID the hand never received came back unsent.
- `nanocode_code_mode::remote::serve_queue(link, queue, wakeups, options, failed)` serves one hand socket from a host's durable command queue, for brains such as tempoxyz/pyramid's broker whose calls are queued in a database and may be sent by whichever replica holds the socket, and is lock-free by design: the host persists nothing before a write and every host call covers a batch. A command's request ID is `QueuedCall::request`, the ID a host's earlier build sent it under, or else derived from its call ID (`QueuedCall::request_id()`, `request_id(call_id)`: FNV-1a folded to 52 bits with bit 52 set, so derived IDs stay below 2^53, JavaScript's largest safe integer, and never meet the `RemoteClient` counter's IDs, which start below 2^52), and a hand treats a request ID as an idempotency key: a Request whose ID is running or retained for the same call attaches to it (a retained reply is sent again) instead of running again, and one whose ID belongs to another call is answered `REQUEST_IN_USE`, which counts as not dispatched. So a command runs at most once per hand runtime however often it is sent, and nothing records "attempted" before a write. A host whose fleet still runs a build that resumes only the request IDs it recorded (Pyramid's `request` column) keeps writing the derived ID there from `admit`, one conditional update per batch, and passes recorded IDs back as `request`, so neither build sends the other's commands under a new ID. The host implements `CommandQueue` (methods return `impl Future + Send`, so a host writes them as `async fn`): `poll` returns every unsettled command for the hand's runtime, sent or not (`QueuedCall` with a host `Origin`; `serve_queue` skips those in flight), `stop` (commands that must not run, with a reason), `cancel` (turns to cancel) and `watch` (turns to tell when they end); `admit` (optional, default `Admit::Send` for all) is one fence over the batch about to be written, answering `Send`, `Wait` (poll again) or `Refuse(reason)` per call; `settle(&[(command, Settlement)])` stores a batch of receipts; `turns_ended(&[(session, turn)])` answers for every watched turn at once; and `unsettled(&[command], error)` hears a failed `settle`, whose commands stay pending. `wakeups` is a stream the function owns (a new command, say), so hosts need no Mutex around a receiver as `CommandQueue::changed(&self)` made them hold. On connect it polls once and resumes every unsettled command through `RemoteClient::resuming`: a retained reply or a finished running one settles, `NOT_RECEIVED` makes the command eligible to send, and a link without `resumes` answers `HAND_RESTARTED`, so those commands settle `Unknown` rather than running twice. It then sends the calls of each poll as one frame batch (`RemoteClient::calls(Vec<(id, operation)>)`, one channel item and so one `link.send`), and one settler task drains every finished reply at once: a reply is `Completed` with its full wire output and acknowledged after `settle` stored it, `NOT_RECEIVED` is sent again unless the command was stopped (then `Unavailable`), another unsent failure (a frame over the limit, a refusal) is `Unavailable`, a failure while the connection is gone is left for the next socket, and anything else is `Unknown`, never retried. A failed `settle` releases its commands, so the next poll sends them again and the hand answers with the retained reply; a `NOT_RECEIVED` for a call this socket sent (a draining hand refuses it) releases it to the next scheduled `busy_poll` rather than to an immediate poll, which made a draining hand and its host loop as fast as they could answer, while one for a command resumed at connect is sent at once; a hand does not retain such a refusal, so `HandActivity::idle()` resolves while it drains (it used to wait for the full drain timeout: on loopback a drained hand went idle and the brain retried once a second, and after `undrain()` the command ran once); a stopped command never sent settles `Unavailable`, and a sent one gets `CancelCall` when `QueueOptions::cancels_calls` (the catalog's `cancels_calls`) is set. It sends one `CancelTurn` naming the turn per session and turn and one `EndTurn` (`Stop`) per watched turn that ended, checking at `QueueOptions::end_check`, polls every `poll` (or `busy_poll` while anything is unsettled or watched) and at once on a wakeup or a released command, and returns the driver's reason when the connection ends or the host's error when `poll`, `admit` or the `failed` future (such as a heartbeat) fails. Before 2026-10-26 the contract was per call: `admit` wrote each request ID before its write (all or none for the batch, so one stale call refused the rest), `recorded` read each command back before settling it, `settle` took one command, and the hand would run a request ID sent twice twice. tempoxyz/pyramid takes one deployment-wide advisory lock (`WRITE_LOCK`) in every write transaction, on a pool of one connection that its reads share, so each of those was a turn through that lock: through a loopback hand (`output/hand-wiring`), 8 parallel calls made 8 `admit`s, 8 `recorded` reads and 8 `settle`s, and now make 1 `admit` and 5 `settle` batches and no reads; a socket dropped 0.5 s into a 2 s command, a command queued while the hand was away and a `settle` that failed once each ran exactly once and settled with the command's real output. The loop owns its in-flight and stopped maps (the settler reports back over a channel, and only retries, `NOT_RECEIVED` or a failed `settle`, poll again at once), and the client's driver runs as its own task, so a slow host `poll` or `admit` never stalls the socket. Under load (`output/hand-wiring`'s `load`: sessions each running Code Mode cells in the brain whose `Promise.all` fans out N nested `noop` calls through `serve_queue` to a loopback hand, 4 cells per session, single runs on a laptop at load average 30-60), 64 sessions x 64 calls went from 3,896 to 25,245 calls/s with cell p50 from 1,001 to 140 ms, 16 x 64 from 10,097 to 24,831, and 64 x 16 behind a host whose calls take 2 ms from 4,752 to 12,638; behind a host that serializes those 2 ms calls under one lock, as Pyramid's write lock does, it stays at about 285 calls/s, bounded by the host's own per-call insert.
- Remote Code Mode payloads cross the connection once. Brains mark their Request frames and hands their Callback frames with `compact: true`, and only answers to a marked frame use the compact forms, so peers built before them keep sending and receiving the full ones: a tool output omits `output` when it is the JSON text of its `structured_result`, as `ToolOutput::from_json` makes it, and the receiver encodes the value again; a nested call omits `structured_result` when it equals `output` and `output` when it is the JSON text of `structured_result`; a completed update omits the input that the call's start update on the same request carried; and a reply names each nested call whose completed update the same request delivered as `{"call_id","delivered":true}`. `SentCalls` writes them on the hand and `ReceivedCalls` in `RemoteClient` restores them before an observer or the execution sees them. A tool output whose `structured_result` equals its `output` crosses with a null `structured_result` to every peer, because every build derives the structured result from the output then. A value holding floats is compared with its JSON text after a parse and a second encoding, because serde_json's default float parsing does not round-trip every value. Requests and callbacks that also carry `output_prefix: true` (RemoteClient's requests and a native hand's callbacks do) accept a text output that ends with its structured result's `output` string as `output_prefix`, the text before it, without `output` (`encode_output(output, compact, output_prefix)`, `SentCalls::output_prefix`); `output_from_wire` and `ReceivedCalls` rebuild the text byte for byte. Codex `exec_command` and `write_stdin` results are such text (a header, then the command output, which `structured_result.output` repeats), so their output crossed twice: on 2026-10-26, through `serve_queue` and a loopback `Hand::connect` hand with a 1 MiB frame limit as tempoxyz/pyramid's broker sets it (`output/hand-wiring`), a 64 KB output's reply went from 141,271 to 70,876 bytes and a 400 KB one's from 880,475 to 440,482, and outputs of 480 KB to 768 KB, which exceeded the frame and settled with unknown outcomes, completed. A hand retains a Call reply for resumes without `output_prefix` (and Execute and Wait replies' full form never used it), because a brain built before it that resumes the request would read the missing `output` as the structured result's JSON; detached cell updates, which can reach another brain after a reconnect, don't use it either. `serve_queue` receipts (`Settlement::Completed`) stay the full form. A brain's own answers to a hand's callbacks don't cross back either: `RemoteClient` marks its requests `answers: true`, a hand then marks its callbacks `answers: true` and records each answer it decodes (`Answers`, by nested call ID), the brain records the same answer under the session and call ID before it sends the `CallbackResult`, and the hand's completed update for that call, when its output, structured result and metadata are still exactly the answer, carries `answered: true` instead of them; `ReceivedCalls::answered` restores them from the brain's record (an `answered` call the brain did not record fails the reply). Records go when used, when their cell's origin finishes (hand `CallbackCatalog::forget`, brain request completion and `DetachedComplete`) and when a session is cancelled or the connection ends, and resumable replies' full form never uses the marker. Brains and hands built before it neither send nor expect the flags, so they keep the full form both ways. On 2026-10-27 in nanocode-ts's `bench/hands.mjs` a cell calling a brain tool with a 1 MiB argument that it echoes back sent 3,073 KB from the hand per turn and now 2,049 KB (the argument still crosses twice: the hand sends the call's start update before its callback, and the two leave on different tasks, so the brain cannot rely on their order), and its turn took 37.6 ms instead of 44 on a native hand and 52 ms instead of 63 on a TypeScript hand.
- A native hand caches the brain callback tools an Execute names (`local_tools`), and a brain sends each list once instead of in every Execute. The hand's catalog says `caches_local_tools: true` (`RemoteCatalog::caches_local_tools`, `RemoteLink::caches_local_tools`, which the native `SocketTransport` and nanocode-ts's Worker link read from it); `RemoteClient` then sends each Execute with non-empty `local_tools` as `local_tools: []` and `local_tools_key`, the BLAKE3 hex of the list's JSON (`local_tools_key`). A hand that holds that key runs the cell with the cached list; one that does not answers `LOCAL_TOOLS_UNKNOWN` before admitting anything, and the client sends the Execute again, under a new request ID, with the list and the key, which the hand stores. The hand keeps the lists its current connection used and, when it reconnects, those its previous connection used (a list moves to the current connection when used again), so a reconnect, such as the redial every `maxDuration` of a Vercel Function, does not send them again, and lists no recent connection used are dropped. So the first Execute of each tool list costs one extra round trip, and every later one, from this brain or a brain that took over the same connection (as each drive of nanocode-ts's Vercel adapter does), carries only its source and context. Hands that don't advertise it, such as nanocode-ts's WASM hand, keep receiving full lists. A hand also no longer sends `DetachedComplete` for an origin that an Execute or Wait reply settles (the brain removes its callbacks on that reply), only for detached cells and origins dropped without a reply, so a cell's reply is its only frame. On 2026-10-27 a nanocode-ts Vercel session's Execute was 53,303 bytes (its MCP, subagent and host tool definitions), and through a Vercel Function's WebSocket (`upgradeWebSocket`) to a `nanocode hand` in San Francisco, 79 ms round trip for small messages, it took 213-224 ms against 83-92 ms for the Cancel frames beside it; with the cache, the exec tool call (one World commit before the Execute plus the round trip) took a median 196-309 ms over four interleaved 7- and 8-turn runs, against 379-412 ms without it.
- `RemoteClient` answers a `CancelTurn` without a `turn_id` or a `Cancel` itself when the session has nothing on the hand: no Execute, Wait or Call of this client still waiting for its reply, no cell it knows to be running (a callback origin) and no brain callback running for it. It still writes the frame, as `Immediate` rather than `Durable`, so the hand still ends anything another client left there, but replies `Ok(None)` to the caller once the frame is written instead of after the hand's round trip. Both backends cancel the turn's cells before a turn completes (Claude's `settle_code_turn`, Codex's `terminate_turn_cells`) and the session's runtime cancels its cells when it stops, so every turn with a remote hand waited one round trip at its end and every stop one durable write and a round trip. On a Vercel preview with a hand 79 ms away on 2026-10-27, the time from the exec call's result to the turn's completion went from a median 84-118 ms to 45-46 ms; a busy `CancelTurn` still waits for the hand (loopback: 1.9 ms with a yielded cell, which the hand then reports as not found).

- integrations/process stops a command's process group with SIGSTOP before it sends SIGKILL. macOS delivers a group signal to one member at a time, so with SIGKILL alone a cancelled shell could see its killed child exit and run its next command, such as a redirect that creates a file, before its own signal arrived: `/bin/zsh -lc` scripts killed 2 ms after they started did so in up to 18 of 400 rounds per run on a loaded laptop on 2026-10-19, and in none of 2,800 rounds with SIGSTOP first.
- `RemoteCodeModeHost::with_tool_selection(Arc<dyn HandToolSelection>)` lets a host select advertised hand tools by session ID, backend family and canonical tool name: each backend binds roots and children through `Tools::for_backend`, and `CodeModeExecutors` binds a selected or cross-call target immediately before use, so a late-attached hand sees the child's own family. The selection filters the model contract and travels as optional `selected_tools` on Execute and Call; a native hand fixes it for the session, filters ALL_TOOLS and refuses excluded names before hand routing or tool admission. Brain callback tools keep their existing origin catalog. Policy changes within a live hand session fail, and hosts keep the policy stable for that session. - Model calls classify failures one way on both backends and every transport. `nanocode::http::retry` (`nanocode_http::layer::retry`) follows Anthropic's and OpenAI's official SDKs: a response's `x-should-retry: true` or `false` decides (`should_retry`), otherwise 408, 409, 429 and every 5xx are transient (`retryable_status`), and `retry-after-ms` wins over `Retry-After`. `ClaudeError::Http`, `ResponsesError::HttpRejected` and `HandshakeRejected` and `HostError::HandshakeRejected` carry `should_retry` from every transport path, and a `HostError` from a `layer::Error` is reconnectable when the error is retryable or a timeout. A transient failure is retried in the call within the backend's budget (Claude five attempts, three without tools, stopping at a server delay over 60 s; Codex `max_attempts`, five by default), and cancelling the turn ends the wait; once the budget is spent the turn settles with `Settlement::FailAttempt`, leaving its operation pending for the host to resume (`DurableOutcome::Interrupted`, with a new budget on each resume). Only a definite answer fails the operation durably: `x-should-retry: false`, another 4xx without the header, or a terminal provider error. A Codex auto-compaction that fails transiently records no step outcome, so the resumed turn compacts again. Hosts that refuse a model request for a reason that clears, such as Pact's egress before re-authorization, answer with `x-should-retry: true` and, when known, `retry-after-ms`; a host transport that fails without a response returns `layer::Error::retryable(true)`.
- AgentRuntime serializes open, open_loaded, open_session and durable resume per session id, and an open that finds a live agent returns it with a new `Agent::subscribe` stream instead of fencing it. An adopted agent whose prompt is refused before its turn started with AgentStopped, TurnStopped or a Reopen disposition, or whose store shows another owner, rebuilds its backend through `AgentOwner::reopen` under every existing handle, resumes the pending turns in accepted order and retries once; a prompt call dropped while it heals lets the next one heal, and explicit shutdown or disconnect turns healing off.
- `SpawnBuilder::session_id(id)` names a root session a durable runtime spawns, which is otherwise a new UUIDv7, so a host can key the session by its own identifier, such as tempoxyz/pyramid's thread ID, and reopen it later with `open_session(id)` without storing a generated ID; the session's record, lineage root and durable state are all that ID. `build` refuses it with `InvalidRequest` when the runtime has no durability, and spawning an ID whose session already exists fails with `InvalidRequest`: hosts open it instead. `SessionStore::prepare_session` creates only: its first acquisition fails with `Error::SessionExists` when the stored state already has a session record, checked with a non-fencing peek before acquiring and again inside the acquisition update, so of two concurrent spawns of one ID only one creates it, though on stores whose `acquire_with` acquires before running the update (the default, which `SqlStore` and `MemoryStore` use) the losing spawn of such a race still fences the winner, which then reopens, while the JSONL store's atomic acquisition leaves the winner its owner.
- `SessionEvents::start` merges a root's agent events and subagent updates into batches for an `EventSink` and returns a pump future the host spawns. It coalesces consecutive assistant and reasoning-summary deltas of the same agent, request and item, holds a batch that ends in a delta until the caller's window since the previous delivery elapses or a drain is requested, and `drained` answers once everything received has been delivered, or with the sink's error after a delivery failed. Drain requests reach the pump over a channel, so it holds no lock. `SessionEvent` implements `Serialize` as the hosts' wire format: `{"source":"agent","event","sdk_timing"}` for agent events and `{"source":"subagent","root_session_id","detach","update"}` with a typed `update` for subagent updates.
- `SessionLog::compact_events()` makes `TurnInbox` store agent events without the copies they carry, for hosts whose logs grow with tool results, such as Pact's Durable Object. A stored root event leaves out `protocol_version` when it is 1 and `request_id` when it is the root session's ID; a subagent update's event leaves out only `protocol_version`, since its `request_id` is the child's session ID. A `tool.result` payload stores its result once, and `"derived"` names the field it left out: `structured_result` when that equals the result text (`result`, or Claude's `result.text`), or `result` (Codex) or `result.text` (Claude, which keeps `result: {}`) when the result text is the exact JSON text of `structured_result`, as `FunctionTool` and other JSON tools return; the marker is needed because unknown-outcome and cancelled results have no `structured_result` of their own. `LoggedEvent::expanded(session_id)` restores what was left out, with the result text byte for byte and objects in sorted key order; other events, and every event of a log without the option, come back unchanged. `InboxHost::publish` still receives the whole event; only `page`, `turn_page` and their bounded forms return the compact form, so a host that enables the option expands what it reads. `submit` sizes the input.accepted event in its full form, an upper bound. Assistant deltas stay, because with a 0 ms coalescing window a reply's deltas and its `assistant.message` commit in different transactions and nanocode-ts rebuilds reply text from the deltas it pages; `model.call.*` fields stay because readers take each event alone.
- `AgentEvents::try_recv` returns an event already delivered without waiting. Every event of a turn is in its streams before the turn's result resolves, so a host that drains them after the result reads them all with it; Tokio's `try_recv` spends no cooperative budget, while polling the stream with `now_or_never` does, and once a task's budget of 128 polls ran out it read a backlog as empty: tempoxyz/pyramid's engine lost final messages that way until it wrapped each poll in `tokio::task::unconstrained`.
- Agents whose host asks for it, with `OpenAiBuilder::tool_input_deltas(true)` or `ClaudeBuilder::tool_input_deltas(true)` (through `ClaudeHarness::configure` in a runtime), stream each tool call's input as `tool.input.delta` events (`ToolEvent::InputDelta`: `model_call_index`, `call_id`, `tool` and `text`) while the model writes it: Codex from `response.function_call_arguments.delta` and `response.custom_tool_call_input.delta`, which carries Code Mode's `exec` source, naming the tool as `tool.call` does through `qualified_tool_name`, and Claude from the `input_json_delta` of `tool_use` blocks. Subagents inherit the setting through the builder recipe. They coalesce like assistant deltas, per network read in the event channel and within the caller's window in `SessionEvents`, and their concatenated text is the call's arguments. They are off by default because every `AgentEvents` reader and `TurnInbox` log would otherwise receive and store every tool input twice, and readers that record unknown events would keep them: tempoxyz/pyramid's engine traces every event kind it does not skip, and it learns the text a turn types into pages or processes from `tool.call` events and replaces it whole, which the fragments of a delta would escape.
- `model.call.started` names the prompt cache its request uses. A Codex call carries `prompt_cache_key`, the key its Responses request sends (see the next item), and leaves it out on a Chat Completions gateway such as Workers AI, which sends no key. A Claude call carries `cache_ttl`, `5m` or `1h`, when its request carries cache-control markers, since Claude caches by prompt prefix and has no key; a request without markers leaves it out. The typed `ModelCallStarted` reads both, and `previous_response_id`, which Codex already sent.
- Codex's default `prompt_cache_key` is `nanocode-prefix-` and 32 hex digits of the SHA-256 of the model ID, tool definitions and base instructions (`prompt_cache::prefix_key`), derived once per session from its first request profile and kept in its checkpoint, so sessions and subagents that share a prefix share a key and a child with other tools, instructions or model gets its own. It used to be the session ID (the durable state ID), and on gpt-6-luna a new session's first call read 0 of about 11k prefix tokens from cache, because on GPT-5.6 and later the key only separates cache accounting while OpenAI routes by prefix (https://platform.openai.com/docs/guides/prompt-caching, read 2026-10-25). Custom models add `-<bucket>`, the session ID's SHA-256 modulo 4, since models before GPT-5.6 route by key and overflow above about 15 requests a minute per key; the built-in GPT-6 models get no bucket, which would only split the shared prefix into more cache writes. `CodexBuilder::prompt_cache_key` sets a key and `per_session_prompt_cache_key` restores the session-ID key. A restored session keeps the key its checkpoint holds, so sessions saved before the change keep their session-ID key.
- `SessionLog` and `TurnInbox` in runtime/agent host a session's turns and events for any host that runs SQL, like `SqlStore`: the SDK owns the schema and every statement and the host only runs `Sql::transaction`. `SessionLog` owns the `turns` table and the `events` table in the nanocode Worker's layout (`seq` as the plain integer primary key, a scope column for several logs in one database). `submit` records a queued turn and its `queued` event in one transaction, returns the existing turn for the same prompt and hand, which it compares by a BLAKE3 payload digest so finished turns keep no prompt, and reports a conflict otherwise; `turn`, `pending` and `page`/`turn_page` read status, unfinished turns in admission order and events by cursor or within a turn's own `first_seq`..`last_seq` range, without opening a session; `cancel` finishes a queued turn at once and marks a running one; `interrupted` notes a recovery on a running turn; `import` adopts turns a host recorded before. A turn's result is its `result` event at `last_seq`, and `TurnRecord::report` returns it with the request ID and status. Pending lookups scan the scope's turn rows instead of keeping an index: on Durable Objects a row read costs a thousandth of a written row, and an index entry would add two writes to every turn. `TurnInbox::open` loads or creates the session and starts `SessionEvents` with a sink that encodes each event, attributes it to its request (Codex turn IDs map to the request through the `input.accepted` event that names both), appends each batch in one transaction and hands the logged events to `InboxHost::publish`. `drive` runs one root turn at a time: SDK operations still pending, in accepted order, through `durable_prompt`, then the oldest queued turn, which the SDK accepts only when it starts so `InboxHost::place` can select that turn's hand, and it records the outcome from `durable_outcome` or returns `Waiting` or `Interrupted` for the host to retry or reopen. `TurnInbox::open` leaves the reopened session's interrupted turns to `drive` (`Agent::leave_interrupted_turns_to_host`, which also covers turns a reopen after an ownership loss finds), so a prompt or subagent completion the agent routes meanwhile does not resume them on its own. `TurnInbox::cancel` also cancels the live turn or makes the next drive cancel it on admission, `TurnInbox::steer(target, id, prompt)` steers the running root turn named by `target`, or with `None` whichever root turn runs, with an identified steer, which the backend accepts once per ID, and answers false when that turn is not running, its cancellation was requested or it no longer takes steering (`TurnNotSteerable`, `TurnStopped`), so a host submits such a message as a turn instead; a host that steers only a turn it saw running, such as one whose users share a session, names it, because a steer without a target lands in whichever turn started after the host's check, `settle` reports quiescence, and `InboxHost::finishing` adds host fields such as timings to a result. `SessionLog::retry` records why an unfinished turn waits on a host it cannot reach: the error, the host's kind for it, an attempt count kept in SQL and the next retry time sit on the turn row, its report shows them as `error`, `kind`, `attempts` and `retry_at` until the turn starts or finishes, and a `retrying` event is appended only when the error or kind changes, so retries add no events. Hosts end a turn they cannot run with `finish`, and `drive` cancels on admission, instead of running, an SDK-pending turn whose log record failed or was cancelled meanwhile. The `retry` column came after the first release; a database written before storage formats were versioned gets it when `SessionLog::migrate` adopts it (see the storage format entry). An agent event is stored as `{"source":"agent","event"}` without `sdk_timing`, the host's `annotate` fields or the top-level `timing` of its payload (1.4 KB of each `model.call.completed`), while `InboxHost::publish` receives the whole event under the same seq; subagent updates are stored whole. `TurnInbox`'s futures are `Send` natively, so a native host drives it from `tokio::spawn` as gakonst/nanocode-swift does; `prompt` used to hold a `&Turn` (whose result future is not `Sync`) across the cancel of a turn cancelled while it was admitted, which made `drive` not `Send`.
- `SessionLog` and `SqlStore` version their storage formats. Each owns an ordered, append-only list of `Migration`s per dialect and records the number it ran in the shared `nanocode_formats` table under its component name (`session_log`, `records`), so several components can keep tables in one database. `SessionLog::migrate()` and `SqlStore::migrate()` run the missing migrations, each with its version update in one host transaction, (`SqlStore::migrated()` skips the check on an instance whose host ran `migrate()` at startup: up to date it still sends `CREATE TABLE IF NOT EXISTS nanocode_formats` and a read, which a host that opens a store per turn, as Pyramid does on its single write connection, sends every turn) and fail with `StoreError::UnsupportedFormat { component, stored, known }` without touching the tables when the database records a format newer than the build's `FORMAT`; both still migrate on their first operation when the host did not call `migrate`. Hosts call it where they open storage, so a host that runs several builds against the same data, such as Pact's Durable Objects during a deploy (an object can be reached by the previous Worker version for a while, and threads are kept indefinitely and migrate forward), refuses storage a newer build wrote instead of reading a format it does not know, and can surface that refusal as a retryable error at a point it controls. A deployed migration is never edited or removed, and a change in what stored rows or JSON mean gets a migration too. Migration 1 is each store's existing schema; for `SessionLog` it also adopts a database written before versioning whose `turns` table lacks the `retry` column (`MissingColumn`), the only conditional ALTER, which replaces the per-process `pragma_table_info('turns')` check. `migrate_format(host, component, migrations)` is the shared runner.
- `SessionLog::replace_queued(request_id, edit_id, text)` edits a queued turn's prompt in place for hosts whose users revise a message waiting behind a running turn: the text replaces the prompt's first text input and drops its other text inputs, while its images and other inputs, their order, its transcript and hand, its request ID and its place in the queue stay. The update and its receipt, a `replaced` event naming `edit_id` and the digest of the edit's text, commit in one transaction, so `Replaced::Applied(Some(event))` comes back once and a retry with the same edit ID and text answers `Applied(None)` whatever state the turn reached since, without undoing a later edit; the same ID with other text is `Conflict`, a turn that is not queued and holds no receipt for the ID `NotQueued`, and an edit whose row, receipt or input.accepted event would exceed `logical_limit` `TooLarge`; an edited prompt above `value_limit` spills into `log_parts` in the edit's transaction as a submitted one does. The update is conditional on the prompt digest it read, and when another writer changed the prompt in between it reads the turn again and applies the edit to the new prompt. A submit retried with the original prompt after an edit reports `Conflict`, since the request ID now holds other content. `TurnInbox::move_queued(queued_id, target)` moves a queued prompt into the running turn as an identified steer under the queued turn's request ID and then dequeues the turn as cancelled with `steered: true` (`SessionLog::withdraw_steered`, conditional on the digest that was steered). The running turn's durable steer receipt is the only decision: `Agent::steer_receipt(id, prompt)` (`LifecycleBackend::steer_receipt`, `DurableSession::steer_receipt` for both backends' policies) answers `SteerReceiptStatus::Accepted`, `Absent`, `Different`, `Withdrawn` or `Unknown` from the session's identified steer receipts, `Absent` only when the driver holds every receipt (no terminal receipt limit, sealed receipt pages loaded, history never pruned) and `Unknown` otherwise or without a durable policy, and `drive` withdraws instead of running a queued turn whose ID already has an `Accepted` receipt for its prompt. So a crash between the steer and the dequeue neither loses nor repeats the prompt, and repeating the move answers `MovedQueued::Moved`; `NotRunning` leaves the prompt queued, `Conflict` means a steer under that ID carried other input or was withdrawn, and `Unknown` moves nothing. A moved prompt shares the running turn's outcome, and one edited after its steer was accepted stays queued and runs its new text.
- `SessionLog::value_limit` is the host's physical UTF-8 binding and row budget; `logical_limit` separately retains the optional prompt admission, event omission and result failure policy. Only owned event-body and prompt slots spill into immutable content-keyed `log_parts`, in the same transaction as their row; each part fits the physical budget including its key and SQLite record header, is verified against its BLAKE3 key when read, and is never replaced or deleted. Reference-shaped user bodies are stored as parts too, and only owned read columns are decoded. Imported prompts spill before JSON batching, whose bindings respect the physical limit; an imported row that cannot fit fails before writing. Small values keep the same row writes. `page_bounded(after, limit, max_bytes)` budgets decoded event JSON UTF-8 bytes before loading parts, excludes the crossing event except that the first event is always returned (also for zero bytes), and leaves the cursor on the last returned event; envelope bytes are outside the budget. Inline logs remain readable; binaries without this contract cannot read spilled values. Bounded pages require a positive event count.
- `SessionLog::logical_limit(bytes)` optionally bounds logical row and event sizes independently of physical storage. Rows are sized conservatively by SQLite's record format (https://www.sqlite.org/fileformat.html#record_format): one varint for the header size and one per column, at most 9 bytes each, the text columns' bytes and at most 8 bytes per integer column. `append` logs an event above this logical limit as `{"type":"omitted","request_id","source","event_type","bytes"}`, and `finish` records an oversized result as a failed one whose error names its status and size. `submit` answers `Submitted::TooLarge { bytes, limit }` without writing when the logical turn row or its input.accepted event would not fit; that event is sized as `TurnInbox` stores it, with the request ID, UUIDv7-length identifiers or the request ID where a resumed turn uses it as its turn ID, and its seq at u64::MAX. Notes and retry errors that hosts add to an unfinished turn are not reserved or spilled and remain subject to the host's physical SQL row limit.
- `SessionLog::blobs(store, threshold)` gives a log the host's `SharedBlobStore` (Send + Sync on WASM too, because `TurnInbox`'s sink is an `EventSink`), so no SQL row holds image bytes or a value above the threshold. `submit`, `replace_queued` and `import` store each base64 data-URL `UserInput::Image` of a prompt as a `BlobUrl` (the decoded bytes under `BlobKey::of`), found with `BlobUrl::from_data_url` before anything is stored, so a `TooLarge` answer puts nothing. The submission digest stays the BLAKE3 of the host's prompt, so a resubmitted data-URL prompt is the existing turn; an edit's digest is of the edited stored prompt. `TurnInbox` hands the runtime the stored prompt, whose BlobUrl images the runtime loads. An event body or prompt above `threshold` UTF-8 bytes, or above `value_limit`, becomes one blob referenced as `{"$nanocode_log":["b3:<hex>"],"bytes":N}` instead of `log_parts` parts, and `page`, `page_bounded`, `turn_page*`, `turn`, `pending` and `import_events`' comparison re-materialize it; BlobUrls inside prompts and event content come back as stored, for hosts to serve from their own store. Every blob is put before the transaction that references it, so a failed put commits nothing. The SDK never deletes blobs: the host owns a session's blob namespace, deletes it with the session and copies the referenced blobs before importing a fork. `log_parts` references written before keep reading, a log without a store behaves as before, and binaries without this contract cannot read blob references.
- `SessionLog::page_bounded` and `turn_page_bounded` size a page without reading the bodies it skips. The window runs over each candidate's `seq` and a lower bound of its decoded size: `octet_length(body)` minus `LONGEST_SINGLE_KEY_REFERENCE`, the 118 bytes of a reference with one `b3:` key and a 20-digit `bytes` field. SQLite (3.43 or later) and PostgreSQL (`textoctetlen` reads only the TOAST header) answer that from the row header. The query then joins `events` for the rows whose running bound fits, and `read_bounded` applies the exact rule before loading any reference: a reference counts its `bytes`, any other body its UTF-8 length, and the first event is always returned. The bound never exceeds a row's decoded size. Inline bodies count exactly and single-key references count 0. A multi-key reference fits only a physical row limit of at least 304 bytes (a 163-byte two-key reference plus 141 bytes of turn-row overhead), so each of its parts holds at least 213 bytes, more than the 67 bytes per key it adds. Pages, `rows`, `has_more` and cursors are therefore unchanged, and the bodies read beyond a page total at most `max_bytes` plus 118 bytes per candidate.

- Third-party storage implements one host interface and leaves every durability rule to core/durability. `KeyValueStore` runs over a linearizable `KeyValue` (get, put_values, compare_and_swap and an optional list_keys). `SqlStore` runs over a SQLite or PostgreSQL `Sql` host whose `transaction(operation, statements)` executes the SDK's statements with text parameters atomically and returns each statement's rows; Durable Objects, D1, libSQL and sqlite-wasm need nothing else. SqlStore owns the `states`, `owners`, `records` and `state_records` tables, which are created by `SqlStore::migrate` or on first use, and every statement: acquisition increments the fence in SQL, a replacement inserts its new records, the state's holds of them and its head only while the owner, fence and expected revision match, and only while the state holds every record it staged, and only when it replaced nothing reads the head in a second query to report Fenced or Conflict (it used to read the head in every replacement transaction, one statement and two row reads per commit that only a refused commit needed), and commit_many sends a group in one transaction with independent outcomes. Counters are decimal text so JavaScript hosts keep u64 revisions, and the fence stops at SQLite's INTEGER maximum. It reports no concurrent handles, so SharedStore groups concurrent commits into commit_many. `list_states` sends a limit above the signed 64-bit maximum as that maximum: PostgreSQL refused `usize::MAX` (`out of range for type bigint`), so `SessionStore::list` failed there. How records are stored and collected is the next entry.
- `SqlStore` stores each record once, by its content key, and notes which states hold it (format 2 of its `records` component): `records` has a row per key (an integer `id`, the unique `key` and the value) and `state_records` a row per record and state that holds it (primary key record and state ID, indexed by state), so the instructions and tool declarations every session of a host names, and any chunk two sessions share, are stored once. A record used to be a row of `blobs` per state, keyed by a hash of state ID and key; migration 2 copies those (and SQLite's `WITHOUT ROWID` `records` of builds before 2026-10-21) into the new tables in one transaction and drops them, and keys no longer collide, so the row-id collision check is gone. A read looks the key up in `records` alone, since a state only reads keys its own payloads name and holds every record its revisions named; `list_records` lists what it holds. A replacement or `put_records` inserts each record whose key is not stored and the state's holds of all of them: on PostgreSQL in one statement whose insert, sorted by key, updates a stored row's key to itself (`ON CONFLICT DO UPDATE`) so it returns the row's id and holds its lock until the transaction ends, so a collection cannot delete it meanwhile and two writers lock shared rows in one order; on SQLite one statement per record and one for the holds. A state holds what its revisions named until it is collected. `SqlStore::unreachable(state)` marks, without a lock, what the current revision reaches: the keys its payload names (`EncodedPayload::references`, each `b3:` and 64 hex digits anywhere in a JSON text, so text that only looks like a key keeps more, never less), followed through the records the state holds with the payload loader, manifests and chunks included, and returns the revision and the held records it does not reach; a state holding a key of an earlier build (neither `b3:` nor `c:`) is kept whole, and a missing or corrupt record fails the mark. `SqlStore::collect(state, revision, keys)` releases one batch in one host transaction: it locks the state's owner row (inserting an ownerless placeholder at fence 0 when the state has none, so a first acquisition waits for it), on PostgreSQL locks the batch's records in key order, and only while the head is still at `revision` releases the state's holds of them and raises its fence, answering `None` and releasing nothing otherwise; it then deletes each of them no state holds any more, in a statement that starts after those locks, so it sees every hold committed by a writer it waited for, and a writer that waits for it inserts the record again. Raising the fence is what makes collection safe without a commit checking every record it names: a writer of the collected state that knew a released record, from a load, an earlier commit or records it put ahead, is fenced, and a writer of any other state names only records its own state holds. `SqlStore::sweep(state, batch)` marks and collects in batches, and `nanocode_store_sqlx::unreachable` and `collect` run them on a host's connection, so a host can check its own state (that no turn runs) and hold its own locks in the transaction. Collect sessions no live driver owns, since a collection fences the owner, and only once readers of an older revision are done; tempoxyz/pyramid sweeps a thread's state a minute after its last turn. On 2026-10-27 against PostgreSQL 18, a copy of Pyramid's dev database (1,498 states) went from 30,972 `blobs` rows of 140.1 MB (94 MB on disk) to 13,598 records of 17.4 MB plus 30,972 holds (25.1 MB on disk with indexes), and `output/storage-check` passed with 8 writers of 150 commits each on states sharing records, half committing through `StagedStore` with records put ahead, beside 3 concurrent collectors: 248 commits were fenced and retried, every head stayed whole and no record was left unheld.
- `nanocode::durability::RecordCache::new(budget_bytes)` is a process-wide cache of durable records for hosts that reopen sessions often, such as tempoxyz/pyramid, which opens every thread's session at the start of each turn and loads it again for its checkpoint: `cache.wrap(store)` is a `CachedStore` that serves `read_record`/`read_records` from memory, reads only the missing keys from the store, writes through every record a `replace`, `replace_to`, `commit` or `commit_many` stores, and forwards everything else, including concurrent handles. Records are immutable and named by their content, so a cached record never goes stale; misses are not cached, and once the budget is spent the oldest entries go first. One `nanocode_sync::Actor` owns the entries, so the cache is lock-free and wrappers on any number of tasks share it. Against a local PostgreSQL 15 on 2026-10-26, reading a session's 300 records of 4 KB took 2.4 ms from `SqlStore` and 0.16 ms warm, and 3,000 took 30.1 ms and 1.25 ms.
- `BlobStore` (core/durability, re-exported as `nanocode::durability::BlobStore`) is the host's store for large immutable bytes, keyed by `BlobKey` (`b3:` and the BLAKE3 hex of the raw bytes). `put` resolving Ok means the bytes are durable, and putting a key again is harmless; `get` returns the bytes or None, and `get_blob` checks them against their key. `BlobUrl` names media whose bytes are in the store as `nanocode-blob:<media type>;b3:<hex>`: `store_data_url` decodes a base64 data URL and stores the raw bytes, and `load_data_url` rebuilds the data URL. The SDK puts a blob before it commits any record that names it and never deletes one: a host keeps each session's blobs in a namespace of its own and deletes it with the session, and a crash between a put and its commit leaves a blob no record names. `MemoryBlobStore` (runtime/durability) keeps blobs in memory for tests and hosts without persistent storage.
- `Sql::dialect` names the SQL its host runs: `SqlDialect::Sqlite` by default, so existing hosts are unchanged, or `SqlDialect::Postgres`, for which `SqlStore` and `SessionLog` (and so `TurnInbox`) send PostgreSQL statements over the same tables and parameters: `$n::text` placeholders, BIGINT identity columns instead of rowids (`states.ord` keeps `list_states` newest first), `json_array_elements` and `->>` instead of `json_each` and `json_extract`, `GREATEST`, `IS DISTINCT FROM`, `information_schema.columns` for the retry column check, `json_build_object` for the retry fields, which keeps their order, and every result column cast to text, so a host returns each column as an optional string; PostgreSQL resolves an unqualified `ORDER BY seq` to the text output column of `CAST(seq AS TEXT)` and sorts `1, 10, 2`, so ordered statements name the table column (`events.seq`, `turns.first_seq`, and `sized.seq` for the outer sort of the byte-bounded event and turn pages). A PostgreSQL `SqlStore` has no legacy `records` table, and its log's `MAX(seq)` lookups are limited to the scope, so a host that serializes a scope's writes (as SQLite's single writer does) gets the same `first_seq` and `last_seq`. Its migrations run through `migrate` or on first use like SQLite's; `CREATE TABLE IF NOT EXISTS` can race between PostgreSQL sessions, so hosts with migrations create the tables first, and a host whose database already has `turns` or `events` tables keeps a log in another schema. `nanocode_store_postgres::PostgresSql` is the tokio-postgres host, running each statement group in its own transaction. PostgreSQL `SqlStore` record inserts and replacements check the owner with `FOR SHARE` on its `owners` row and the replacement's upsert updates only the expected revision, so at the default READ COMMITTED an acquire waits for an uncommitted replacement and then sees it, and a replacement whose owner was fenced or whose revision moved inserts nothing and reports Fenced or Conflict. `SqlStore` is a `StateStore` for any host lifetime, so a host can run it on a transaction it borrows.
- `nanocode_store_sqlite::SqliteSql` is a `Sql` host over one rusqlite connection on its own worker thread (WAL, `synchronous = FULL`, a 5 s busy timeout), so a native host runs `SqlStore`, `SessionLog` and `TurnInbox` over one SQLite file as WASM hosts do over theirs; gakonst/nanocode-swift does. Each `transaction` runs its statements in one `BEGIN IMMEDIATE` transaction with text parameters and returns every cell as text or null (integers and reals as their decimal text); a failure before `COMMIT` rolls back and is `NotCommitted`, a failed `COMMIT` is `Backend`. A transaction the worker received runs to completion even when its caller dropped the future, as `SqliteStore`'s writes do.
- `nanocode-store-sqlx` runs `SqlStore`'s PostgreSQL statements on sqlx 0.9 (the version tempoxyz/pyramid's backend uses, so a host builds one sqlx): `SqlxSql` over any `PgConnections` source (a `PgPool`, or a host's own connections that wait out restarts) runs each statement group in its own transaction, `SqlxTransaction` runs them on a `PgConnection` inside a transaction its caller commits, and `commit_staged(writes, connection)` commits a `StagedStore`'s writes there, so staged session state commits with the host's own transaction; `unreachable(state, connection)` and `collect(state, revision, keys, connection)` run `SqlStore`'s collection there. Each column comes back as an optional string, as `SqlRow` expects. It builds natively only, like `nanocode-store-postgres`.
- `StagedStore::new(base)` wraps any `StateStore` and keeps every acquisition and commit in memory, lock-free (an `Atom` of `Arc`'d states whose payloads and records are `Arc<str>`, so a write copies pointers, not content, and a read looks up its state instead of cloning everything staged; it used to hold a `std::sync::Mutex` and clone every staged payload and record on each read): reads see staged states and records before `base`, acquisitions read `base`'s owner without fencing and stage the next fence, and `StagedStore::writes` returns the `StagedWrites` handle the host keeps. `StagedWrites::commit_to(store)` acquires each changed state in `store` for its staged owner, fails with `Fenced` unless that fence is the one staged (no one acquired it since) and with `Conflict` unless the revision is still the one staging started from, then writes the last staged payload at the staged revision with every staged record through `StateStore::replace_to(state, owner, expected, revision, payload, records)`, which advances a head by more than one revision in one fenced replacement (`SqlStore` implements it; other stores answer `Ok(None)` and `commit_to` replays every staged commit in order, the records with the first, as it always did), so revisions, which durable state payloads embed, match what the session saw and nothing reads the intermediate heads anyway. On PostgreSQL a replacement inserts its records in one statement (`INSERT_RECORDS`, over a JSON array of `[id, key, value]`) instead of one per record; SQLite hosts keep one statement per record, since Durable Objects and D1 bound each value. tempoxyz/pyramid commits a turn's staged writes inside the transaction that holds its deployment-wide write lock, so this is time every other writer waits: against a local PostgreSQL 15 (`output/durability-bench`, p50 of 6 runs), 10 staged commits with 50 records committed in 5.4 ms instead of 23.5, 30 with 150 in 10.7 instead of 67.8, and 60 with 300 in 20.4 instead of 77.6, in 4 statements instead of 2 + records + commits; 60 commits of 64 KB with 300 records of 16 KB (8.4 MB) took 77.8 ms against 70.1, Postgres parsing the 4.7 MB array costing what 358 sub-millisecond loopback round trips did, which across a network each cost a round trip. `commit_to` leaves the writes staged, so a host whose transaction fails to commit can call it again on a new transaction; the host calls `discard` once its transaction has committed, and a `commit_to` after that commit fails with `Fenced` instead of writing twice. `StagedWrites::stage_records(store)` (`nanocode_store_sqlx::stage_records(writes, connection)`) writes every staged record ahead of the host's transaction through `StateStore::put_records`, which stores records no head names yet (`SqlStore`: one statement on PostgreSQL, one per record and one for the state's holds on SQLite; other stores answer `Ok(false)` and nothing is staged ahead), and `commit_to` then sends only the records not staged that way, so the host's transaction holds the acquisition and one head replacement whatever the turn wrote. Records are immutable and content-addressed, so writing them early exposes nothing, and a turn whose transaction then fails leaves records nothing names, as a crash between a blob put and its commit does, which the state holds until a collection releases them. `commit_staged` and `stage_records` skip `SqlStore`'s format check (`migrated()`), which the turn's own store ran on its first read. Against a local PostgreSQL 15 (p50 of 6 runs), the transaction of a turn with 10 commits and 50 records took 0.7-0.9 ms instead of 4.2-7.1, and one with 60 commits and 300 records of 16 KB 0.9 ms instead of 76-82, the records going in 3.8-78 ms before it; tempoxyz/pyramid commits inside the transaction holding its deployment-wide write lock, so this is the time every other writer waits per turn. Staged states have no events or summaries. Give `commit_to` a store that runs on a transaction the host commits or rolls back, such as an `SqlStore` over the host's transaction, so state commits atomically with the host's own writes: tempoxyz/pyramid opens each turn's `SessionStore` over a `StagedStore` of its PostgreSQL `SqlStore` and commits the staged writes in the transaction that sets the turn's final status, only when the turn succeeds, discarding them after that transaction commits, so a failed or cancelled turn leaves the model context of the last successful turn. A session over a `StagedStore` ends when its writes are committed or dropped. `StagedWrites::changed_states()` lists the states with staged changes and `retain(keep)` drops every other staged state before `stage_records` or `commit_to`, so a host that runs subagents within one turn can commit only its root (`retain(|state| state == root)`): its children and the `<root>:subagents` journal are then never written, and the next turn's root finds no journal and resumes or announces no child of an earlier turn, which tempoxyz/pyramid's review of PR 219 asked for. `keep` may run more than once and must be pure.
- `SessionStore::export_branch(id, at)`, `export_page` and `import_branch` move a settled branch into an independent store, which the same-store `branch` cannot do, for hosts that keep one store per conversation, such as a Durable Object per thread that forks a thread into a new object or runs a throwaway fork for a review. `BranchExport` is small: the source record, the boundary, the selected checkpoint's key, the number of covered turns and the key of an inherited-turn index, a `Sequence` of `{turn, checkpoint}` records (with `before` where the checkpoint before a turn is not the previous turn's, as at an import's first own turn) behind a record that also names the history's start. `export_page(id, export, cursor, max_bytes)` recomputes the covered history from the source on every call, so the source keeps nothing between pages, and fails when retention or a rewrite changed it; its pages walk the start checkpoint, the settled checkpoint of every covered turn, the selected checkpoint and the index, each as the physical records its root reaches (inline payloads, manifests, tree nodes and chunks) minus those the previous root reaches, in key order, and hold at least one record and stop before the record that would pass `max_bytes`. Records are found by following keys held as JSON strings, which is how `EncodedPayload` serializes, so every checkpoint format transfers without format code, and a page call keeps only the key graph of the checkpoints it walks and reads the previous root's records once, instead of a key list for the whole history or a walk per turn. The imported record keeps the index key, not a growing metadata list, so the copy can be branched in its own store or exported again through the turns it inherited, after its source is gone: Through takes the entry's checkpoint, Before the checkpoint before the entry, the history's start or the checkpoint the import began from. Exports allow pending operations after a Through or Before boundary and refuse Latest while any is pending. `import_branch` acquires the target once and commits a staged head whose record holds the import's next cursor; `SessionStore` treats that head as absent (load, resume, turns, list and branch), and a session described over it replaces it. `BranchImport::import(page)` verifies every record against its content address and its kind's size bound (inline payloads and manifests below 16 KiB, chunks at most `CHUNK_MAX` plus a UTF-8 boundary), rejects records it cannot verify, such as the chunked payloads of SHA-256 builds, ignores a page that ends at or before its cursor, refuses one that starts after it and commits the page's records with the advanced cursor in one fenced commit, so a host that loses an import calls `import_branch` again and continues from `next()` without counting SDK rows. `publish` refuses an incomplete import, hydrates the selected checkpoint and checks every indexed checkpoint root, then makes the session visible in one fenced commit; `import_branch` of an export already published returns it without writing. The session log moves separately, through `SessionLog::import` and `import_events`.
- `SessionLog::import_events(after, events)` writes the events another log's `page` returned under their own seq, request ID, creation time and body, so a host that forks a conversation into a new store, such as a Durable Object per thread, copies its log as well as its durable state: with `import` given each copied turn's `first_seq` and `last_seq`, which keeps it from synthesizing a result event, the target's `page` and `turn_page` answer the source's events for the copied range and its turns report the same results. `after` is the cursor the events follow, as `page(after, limit)` takes it; the events must ascend above it and fit `logical_limit`, bodies above `value_limit` spill into `log_parts` as appended ones do, and the call answers the last imported seq, the cursor for the next page. A read transaction finds where the target's log ends and reads back the rows in the range, and the import is refused before anything is written when the log ends before `after`, holds a different event at an imported seq (every column is compared, a spilled body after reading its parts back), holds an event of its own in the range that the import lacks, or another scope owns an imported seq. A write transaction then inserts the remaining events in order, each only while the log still ends at its predecessor, which is a primary-key lookup instead of a scan of the scope, so a replayed or retried import writes nothing and continues where a lost one stopped, and an append that lands between the two transactions fails the import instead of interleaving with it. On PostgreSQL the write also moves the `events` identity sequence past the imported seqs with `setval`, because explicit values do not advance it and the next `append` would collide. The seq is the primary key of an events table that every scope in a database shares, so the copied log needs seqs that no other scope in the target uses, as a fresh store per conversation provides. Copying with `append` cannot do this: it renumbers events, replaces their creation times and duplicates them when retried.
- StateStore: `peek` is required, because SessionStore::load, resume, branching and child journals read through it without fencing, and `owner` reports the current owner token without fencing; its unsupported default makes AgentRuntime treat a live agent's ownership as unknown. `acquire_with` runs its owned, synchronous StoreUpdate once against the acquired state; updates only calculate, None acquires without changing the revision, and the default acquire-then-replace reports failures after acquisition as Backend errors. `acquire_with_companion` acquires a distinct companion with the primary: an equal companion is NotCommitted before any write, NotCommitted means neither state changed, any other error leaves both uncertain, and a batching adapter validates both fences and revisions first and acknowledges only once the whole batch is durable. `commit` checks the fence and revision like `replace`, replaces the payload, advances the revision once, inserts absent records and appends events atomically; conflicting record content or a seq overflow is NotCommitted before any write, the default rejects events with NotCommitted, and events take contiguous seqs after the state's last, from 1, never reused. `commit_many` returns one result per commit in order, each judged on its own fence and revision; a shared write acknowledges none before it is durable, and a failed group may leave any subset committed. `supports_events`, `supports_summaries` and `batches_companion_acquisition` stay fixed per adapter and wrappers forward them; `concurrent_handle` returns a handle only when operations stay correct concurrently, including on one state; `flush` is an ordered barrier. `list_records` returns every record key of a state, for repairs that must find records by content; it is unsupported by default, and SqlStore, KeyValueStore (over `list_keys`), JSONL, SQLite and Postgres implement it and SharedStore forwards it.
- StateReader never acquires, fences or changes a revision: `read_state`, `read_records` and `read_events` are strongly consistent per state, while `query_states` and `query_events` come from an index that may trail commits. A summary belongs to the revision that committed it; index updates are idempotent by (state_id, revision) and (state_id, seq), Remove keeps a tombstone that queries never return, and an asynchronous indexer persists the publication intent in the commit's transaction. `query_states` orders by (updated_at_ms, state_id) and `query_events` by (at_ms, state_id, seq), both descending, and `read_events` by seq between exclusive bounds; pages are live keyset pages, a zero limit returns an empty page, `usize::MAX` is valid and adapters impose no hidden caps. scope, parent, state_id and attributes match exactly, kinds match any listed kind, and text is an ASCII-case-insensitive literal substring of the title, preview or event texts.
- Payloads are BLAKE3-addressed: one inline `b3:` record under 16 KiB, otherwise content-defined `c:` chunks under a manifest keyed by its own hash. A manifest that would reach 16 KiB becomes a tree cut where a hash prefix is divisible by CHUNK_AVG / 64, so a save rewrites only the groups around its edits: on a 60-turn, 4 MB local Claude session manifest bytes fell from 2.39 MB to 1.55 MB. Keys without `b3:` are SHA-256 records from earlier builds that still load and verify, and `EncodedPayload::matches_key` treats a SHA-256 key of the same content as equal, so receipts and step inputs recorded before the change still match. Records are immutable, and a store deletes one only after fencing every writer that could know it (`SqlStore::collect`), so a session driver counts every record its loads read (the latest checkpoint at agent acquisition and `LoadPayload(s)`, through `EncodedPayload::load_noting` and `load_many_noting`) among its committed records, and the first save after a restore stages only chunks the load did not read: before, it resent every chunk of a re-encoded checkpoint, and in the Worker's `measure-store.mjs` on 2026-10-20 a Claude turn restored after 60 turns of 200 text deltas sent 172 statements and 2.29 MB over the WASM bridge, against 71 and 1.31 MB now and 70 and 1.24 MB for a warm turn, and took 43.0 ms instead of 48.3 ms. `SessionStore::record(id)` is a session's `SessionRecord` (its model, lineage and settings) without the first prompt `summary` also reads, for hosts that only ask whether a session exists and which model it runs, as tempoxyz/pyramid does before every turn. `SessionStore::load` keeps the checkpoint payload it read and the record keys that load noted, `prepare_resume_loaded` hands them to the session with the checkpoint preload, and the driver's agent acquisition uses them instead of reading and verifying the checkpoint again while the state's latest checkpoint key still matches, since records are immutable; the Claude backend takes the loaded value from the preload as Codex does instead of decoding the payload again. The load also notes the records a format's `CheckpointFormat::hydrate_noting` reads, Codex's history pages and items, and `DurableSession::take_checkpoint_preload_with_records` hands them to the Codex backend, which remembers them instead of re-encoding and hashing the whole history to check the checkpoint key; `load_many` reads the manifest levels and chunks of every payload it loads in one store read per level instead of one per payload; `prepare_resume_loaded` skips its head peek when the load found a session record; and `StoredSession::checkpoint_thinking` reads Codex's thinking without converting the checkpoint.
- Durable state transactions grow with their content, not with history: `EncodedPayload` binds at most one chunk (under 32 KiB) per record and `SqlStore::replace` sends one statement per new record on SQLite (one for all of them on PostgreSQL), but an image held inline still costs a megabyte-scale transaction and its whole size again on every reopen, which a blob store avoids.
- Step inputs and outputs under 1 KiB (`STEP_INLINE_BYTES`) that a driver holds with their content are written inside the state row as `"=<json>"` instead of as `b3:` records, so a step's payload costs no row of its own: a model call's `{"wire","blake3","bytes"}` input, its output that references the message records, and a tool call's input. `OperationState`'s staging keeps their content, since the state row is rewritten on every commit while the step lives, and still stages their child records. Steps retire at the next `ExecutionAdvanced` or completion, so an idle session's head carries none. A head with any inline step has state format 6, which older builds refuse as an unsupported state format instead of failing on a missing record, and other heads keep format 4 or 5, so a rollback reads every session that is not mid-turn. In a Node sqlite harness on 2026-10-25 (nanocode-ts Code Mode, trivial `text("ok")` cells) a cell committed 5.1 rows and 10.1 statements to the store instead of 8.1 and 15.1 (with 5 event rows either way), and in the Worker's `measure-store.mjs` a Codex turn with three tool rounds wrote 58.5 Durable Object rows instead of 64.5 and read 176 instead of 224.
- Durable per-step work grows with new content, not with history (`EncodedPayload` trees, `SequenceLog`, Claude's incremental tool-ID sets, the receipt archive; see those entries). Through gakonst/nanocode-ts's Node harness (`scripts/profile-turns.mjs`: a mock provider, one host tool call per turn, node:sqlite on disk) on 2026-10-26, a Claude turn's WASM time at turn 600 went from 11.0-14.1 ms to 4.1-6.1 ms (3.4 ms at turn 50) and a Codex turn's from 13.3-14.6 ms to 4.9 ms (3.8 ms at turn 50). `SessionSnapshot` keeps the model's `ResponseHistory` (its committed segments shared, serialized as the same array) and its request prefix as the model's `Arc`, so taking a snapshot copies no items, and `DurableExecution` encodes completions, failures, cancellations and standalone checkpoints through the continuation cache (`prepare_cached_snapshot`, `prepare_cached_completion`): the snapshot diffs against the history the last continuation encoded and attaches the `SequenceLog` frontier, where each turn's snapshot used to clone and re-encode the whole history. The cache is held across the commit and released only once it succeeds. A reopen after each run resumed with every message, and the Worker's measure-faults passed 1,220 checks on every scenario but legacy, which needs a bundle from an older SDK.
- `Sequence` in runtime/durability stores a list as one content-addressed record per item: each run of 16 item references is sealed into an immutable group page and each 16 pages of a level into a page of the next, and the payload holding the sequence keeps `{"tail":{"levels":[...],"items":[...]}}` with fewer than 16 unsealed references per level, so a save writes its new items, at most one page per level and references that grow with the logarithm of the length. `SequenceLog` keeps a sequence incrementally: `sync(unchanged, items)` truncates it to the unchanged prefix and pushes the rest, sealing a page whenever a level fills, and each sealed page carries its 16 entries as child payloads, so `frontier()`, the unsealed entries of every level, reaches every record of the sequence through the pages' children, and `sequence()` is the frontier's references. Backends attach the frontier to the payload that holds the sequence, so a save hands the driver O(16 log n) payloads instead of every item and page, and `release()` turns the entries into references once their commit is confirmed (Codex releases after `commit_writes` succeeds; Claude's items keep their content on their `HistoryMessage` anyway). `PagedWriter::sequence` builds a sequence from scratch for exports and full snapshots. `load_sequence` reads each level in one batched load and still reads the chained 64-item pages (`{"tail":"<key>"}`) of earlier builds, whose every save rewrote the tail page, while older binaries fail to parse a sealed tail instead of reading an empty history. `EncodedPayload::with_payloads` attaches the records a payload references, and the driver stages only those its committed records lack, including records its loads read, so callers need not track what is durable. Staging walks a payload's tree by reference and skips a node whose key is committed together with everything under it (`stage_tree` checks the node before its children), which holds because a commit stages a record's whole closure minus records already committed, and `EncodedPayload`'s children and pending records are `Arc` slices, so cloning a payload, as transitions and the cursor caches do, copies no list.
- The SDK's Claude durability policies set `ClaudeExecutionPolicy::pages_messages`, so root checkpoints and cursors are version 4: each conversation message and each retained Code Mode round (`conversation.code_calls`) is its own record, cached on its `HistoryMessage` or `CodeRound` beside its JSON, a checkpoint is `{"provider":"claude","version":4,"messages":<Sequence>,"code_calls":<Sequence>,"admitted_base","admitted_tool_ids","unadmitted_tool_ids","snapshot":<version 1 snapshot without them>}` and a cursor `{"version":4,"messages","code_calls","admitted_base","admitted_tool_ids","unadmitted_tool_ids","pending":<the whole working list>,"template":<record of the template's system and tools>,"cursor":<version 1 cursor without them>}`. The admitted IDs that no `tool_use` block of the stored messages carries are split by when they were admitted: those admitted before the last settled checkpoint, such as every ID of compacted messages, are one record `{"ids":[...]}` named by `admitted_base`, and the rest are listed in `admitted_tool_ids`; `unadmitted_tool_ids` are the `tool_use` IDs that are not admitted, all sorted, so the set is rebuilt exactly. `Conversation.admitted_tool_ids` is `AdmittedIds`, the IDs in admission order with their positions, and the durable `Paging` keeps the three sets incrementally: a save lists and unlists only the `tool_use` IDs of messages that changed since the last save (found by `HistoryMessage` pointer identity) and classifies only the IDs admitted since, and the base record is re-encoded only when a compaction or rewind changes it. Each save used to collect every listed ID into a set and scan every admitted ID, and after a compaction every cursor carried every earlier ID. A model call's receipt names its assistant message by `content_record` instead of repeating its content, and a completed turn's output names the last assistant message by `final_record` when its text blocks are the final message; both records are the ones the history pages reference, so a reply is stored once instead of three times. `ClaudeCheckpointFormat::hydrate_noting`, the policy's continuation, step replay, admission replay and acquisition rebuild version 1 values, so everything that reads a checkpoint as a value is unchanged; version 1 to 3 checkpoints and cursors (version 1 cursors with `pending_base`) still load, forks, compactions, developer-notice checkpoints, subagent child states and exports stay version 1, and older binaries reject version 4.
- KeyValueStore keeps a state's head at `{prefix}state/{state_id}` and its content-addressed records at `{prefix}record/{state_id length}/{state_id}/{key}`, written before the head swap and never deleted, so a failed replace leaves only unreferenced records. Versions are `fence.revision.owner` strings the adapter chooses and hosts store and compare verbatim; a failed swap rereads the head to report Fenced or Conflict, and acquisition retries until it installs the next fence. compare_and_swap must be linearizable per key, so eventually consistent stores such as Cloudflare KV cannot back it.
- runtime/durability session drivers: SessionStore::session and resume and DurableSession::open, open_shared, open_shared_described and open_sibling acquire ownership and persist the record before returning, fencing earlier owners. prepare_session, prepare_resume and prepare_shared_described return a driver without writing, and its first command acquires once through acquire_with with the prepared record merged, which JSONL commits with one disk sync, so use them only where construction consumes the driver at once. `acquire_agent_with_initial_checkpoint` commits the backend's initial checkpoint in that acquisition when the state has no record, checkpoint or operations and returns `InitialAcquisition::Existing` otherwise, and `seeded_child_journal` with `acquire_agent_with_initial_checkpoint_and_journal` folds the subagent tree acquisition into the same synced batch only when the store batches companion acquisition, never on WASM. NotCommitted acquisition failures may be retried; other failures poison the driver. Startup durability is bounded by disk syncs (0.6 ms each with the JSONL store's F_BARRIERFSYNC on APFS, 5 ms with F_FULLFSYNC), so measure entries, syncs and latency when changing acquisition paths.
- `DurableOwner::commit_writes` applies one operation's `OwnerWrite` values in order with one commit and one revision; nothing commits when any write fails, and a BeginStep for an existing step returns its Interrupted or Replay outcome without writing (three commits per tool step took 5.9 ms instead of 18.6 ms). `DurableSession::stage` queues a `SessionWrite` onto the driver's next commit of any kind, including a live agent's owner commits. NotCommitted keeps it queued; any other error peeks the state: the payload at the expected revision means the commit landed, the previous revision is retried once with the same revision-conditional commit, and anything else poisons the driver. `append` commits staged writes at once, `commit_checkpoint` commits a standalone checkpoint with its write, and after either fails with NotCommitted flush with an empty append, because retrying the same write duplicates its events. `MetadataWrite` is a data-only compare-and-set that cannot change identity fields. `DurableOwner::abandon_stale_kinds` registers maintenance kinds, Codex standalone_compaction and Claude compact and session_end, that the driver cancels when unclaimed at the head of the pending queue: once when they are registered, which each backend does right after its owner acquires the session and before any attempt of its own, and again before each admission, attempt and standalone checkpoint; prompt turns are never abandoned.
- A durable state's head keeps its pending operations, the terminal receipts accepted after its last sealed one and references to sealed receipt pages instead of every receipt. Before each commit of a driver without a terminal receipt limit, `JournalState::seal_receipts` seals each terminal receipt that no pending operation precedes into an immutable content-addressed page record of its own (`RECEIPT_LEAF`), and each 16 page references of one level into a page of the next, so the head holds no terminal receipt and fewer than 16 references per level; it used to seal runs of 16 receipts and keep up to 15 in the head, which every commit rewrote, and a Claude tool turn's six head writes now total 11.5 KB instead of 23.7 KB for one extra 0.4 KB record (nanocode-ts Node harness, 100 turns, 2026-10-26); a limit keeps its retained receipts in the head and seals nothing. `SessionStore::with_terminal_receipt_limit(limit)` gives that limit to every session the catalog opens (`session`, `prepare_session`, `resume`, `prepare_resume`, `prepare_resume_loaded` and the Claude and Codex backends' own acquisitions, and their siblings), as `DurableSession::open_with_terminal_receipt_limit` does for one; without it they keep every receipt, and with it each finished operation past the limit leaves the head with its input, output and checkpoint, which a collection then releases. In `output/storage-check` on 2026-10-27, a catalog session of 12 operations, each with three 4 KB continuations and swept after each, held 5 more records every operation without a limit (60 after 12) and 7 from the fourth on with a limit of 1. Every receipt stays available: the driver's acquisition, `SessionStore` reads, `SessionReader::state` and `CheckpointBranch` load the pages, one record read per level, before they use the operations, so idempotent admission, replay and rewind see all of them, and accepting an operation before they are loaded fails. Loaded and sealed receipts live in `JournalState`'s archive, an `Arc` beside the head's own operations that sealing extends (cloning it once per 16 receipts when a transition holds the previous state), so cloning the state for each transition, the prior-operation check of every transition, staging and the head's serialization touch only the head; `operations()` is an `Operations` view over both, and `first_accepted()` answers the oldest without a scan. They used to share one map, which every transition cloned and scanned whole. A head that references pages is state format 5: format 4 heads load and are sealed on their next commit, a head with nothing sealed is still written as format 4, and older binaries reject format 5. Tools that read operations from a stored head follow `sealed.levels` to the page records, as the Worker's measure-faults does.

- store-jsonl takes no file locks: the single O_APPEND journal is the linearization point and keeps owner fencing across processes. A writer replays the tail, validates, appends its entries with one write and one disk sync, then replays everything that landed before them and judges its own entries by the rule every reader applies: an acquire needs the next fence and a replacement the current owner and the next revision. On Apple platforms that sync is `fcntl(F_BARRIERFSYNC)` (`sync_journal`; `sync_all` where the filesystem refuses it), which writes the entries to the drive like `fsync` and orders them before any later write: an acknowledged commit survives a process or OS crash, and a power loss can lose only the latest commits, never reorder them, where `sync_all`'s F_FULLFSYNC also flushed the drive's cache. Every durable commit used to pay that flush: on 2026-10-27 on an M1 Max (APFS) a 2 KB append took 5.15 ms with F_FULLFSYNC, 0.64 ms with F_BARRIERFSYNC and 0.04 ms with `fsync`, and a native brain's turn (6 commits: admission, two model steps, the cell, completion) with an empty Code Mode cell and a scripted model took 33.9 ms and now 4.8 ms (`output/native-brain-bench`, a temporary `brain_bench` example over `ClaudeClient::messages_api` and `JsonlStore`; with `MemoryStore` 2.1 ms). The SQLite store already synced with `fsync` (`synchronous = FULL` without `fullfsync`). Other platforms keep `sync_all`. Superseded entries are skipped by every reader and reported as Fenced or Conflict, or retried for acquisitions, and a fence, revision or owner fence beyond the next one is corruption. Multi-entry batches carry a batch id and count and apply all or nothing, commit_many appends independent unbatched lines, a writer after a torn tail starts with a newline, and readers never truncate. Every process sharing a journal must run this protocol; older binaries lock and truncate, so restart every writer after upgrading.

- Write lock-free code: no Mutex, RwLock or Condvar from std, Tokio, futures or parking_lot anywhere in the workspace. - nanocode-sync semantics: `Atom::update` clones the value, applies the change and retries the compare-and-swap, so a change may run more than once and must be free of side effects; `try_update` skips the store on None and `modify` on an error. `Signal` fires once for current and future waiters (its sender sits in a `Slot`, so firing and dropping one write no arc-swap value), `Slot` put and take swap atomically and never read in place: `is_empty` reads an occupancy count kept beside the value, because loading the value for the check made a concurrent take or put find it shared and drop it. Its value is a crossbeam-utils `AtomicCell<Option<Box<T>>>`, one pointer-sized atomic swap (lock-free on every target, since the type is pointer-sized), not an `ArcSwapOption`: arc-swap's default strategy makes every store, swap and compare-and-swap pay the outstanding read debts of every thread that ever loaded through arc-swap (`Debt::pay_all`), which a `Slot`, never loaded, gains nothing from. In a `sample` profile of 200 concurrent Claude sessions `pay_all` was 59% of the process's CPU, mostly the event channel's per-event `Slot` swaps; with `AtomicCell` 10,000 one-turn sessions (`claude_pool` binary) used 2.59-2.67 s of user CPU instead of 4.14-4.41 s and first-turn p50 fell from 12.4-15.0 ms to 8.6-9.2 ms, and Codex sessions (`pool`) 6.80-6.85 s instead of 7.60-7.73 s. `Inbox::drain` loads the head first and returns without a swap when it is empty, which every event's drain was. `Ordered` delivers values in ticket order, so every ticket must be published exactly once. `Inbox` pushes by compare-and-swap and drains in push order. `SingleFlight` runs one future per concurrent burst, and a cancelled leader hands the flight to the next caller. `Sequencer` admits one `Turn` at a time in arrival order, and a cancelled `enter` passes an admission it already received on. Until a caller first has to wait, a sequencer admits and releases with one compare-and-swap on a mode byte (free, held), touching no `Atom`; the first `enter` that finds it held switches it (through a brief `switching` mode, which the holder's release spins past) to the queued mode, records the fast holder in the queue as its holder and waits there, and from then on every turn goes through the queue as before, so arrival order and cancellation behave as they did. 300 rounds of 64 tasks making 50 `enter`/`try_enter` attempts each, some cancelled by a 20 us timeout, held no two turns at once and deadlocked none, and `Owned` counted 64,000 of 64,000 increments (`output/hand-wiring`, `sequencer` binary); 10,000 one-turn Claude sessions used 1.91-1.93 s of user CPU instead of 2.63-2.66 s, first-turn p50 6.7-6.9 ms instead of 8.3-8.9 ms. Every arc-swap store (each `Atom` update, `Inbox` push, queued `Sequencer` turn and `Signal` fire) pays the read debts of every thread that ever loaded through arc-swap, exited threads included: 75 ns with no other threads, 0.4-0.5 us with 8, 1.3-1.5 us with 32, 4.6-6.4 us with 128 and 17-21 us with 512, staying at the high-water mark (`output/arcswap-scan`), so keep frequently written state out of `Atom`s (in an owning task or a `Slot`) and SDK state away from large or growing thread pools. `Owned` moves its value to the admitted caller as `Held` or `Leased` and back before the next turn. `Actor` runs jobs on its own task in call order and cancels a job whose caller drops its future; it needs a Tokio runtime natively or an installed platform host on WASM.
