# Prompt: benchmark agent CLIs

Paste everything below the line into a cloud agent that has this branch checked out.

---

Benchmark the `nc` (nanocode) CLI against five other agent CLIs and produce a report with the raw data. The harness is in `bench/cli/` of this repository (branch `cli-bench`); read `bench/cli/README.md` first. Work only inside `bench/cli/`, commit to this branch, and never commit binaries, `node_modules`, `work/` or credentials.

## What to compare

| Lane | CLI | Install the latest release of |
| --- | --- | --- |
| `nc` | nanocode | the `nanocode-cli` release of nanocodexyz/nanocode (`curl -fsSL https://nanocode.xyz/install` shows where the builds are); also build `--profile dist` from this checkout if the release is older than master |
| `fx` | Vercel fx | https://fx.sh (release binary) |
| `pi` | Pi | npm `@earendil-works/pi-coding-agent` |
| `opencode` | OpenCode | npm `opencode-ai` |
| `claude` | Claude Code | npm `@anthropic-ai/claude-code` (or its native installer) |
| `codex` | Codex CLI | npm `@openai/codex` |

Install each into `bench/cli/tools/install/<lane>/`, not globally. Record the exact version, the install command, and the date. Point the harness at them with `NC_BIN`, `FX_BIN`, `PI_CLI`, `OPENCODE_BIN`, `CLAUDE_BIN`, `CODEX_BIN`.

## Rules

1. **No real model, no real account.** Every lane talks only to the local fixture (`harness/fakellm.mjs`) and runs with an isolated `HOME` and config directory, as `harness/lanes.mjs` sets up. If a CLI tries to reach the internet, log in, or update itself, disable that and write down how. Never use or read real credentials.
2. **Make each lane work before measuring it.** Run `node harness/smoke.mjs --only=<lane> --dump=/tmp/dump`. A lane works when the headless run exits 0 with one `stream` request and the last token on stdout, and the terminal run reports a first frame and `max_token` 199. `python harness/screen.py work/smoke-tui-<lane>.bin` prints what the terminal showed, which is how to find an onboarding or trust dialog and the right `marker`. Fix `lanes.mjs` until all six pass, and update each lane's `verified` note.
3. **Same work for every lane.** Same prompt, same fixture stream, same terminal size (120x40). Where a CLI cannot do something (for example it prints only at the end), report that as a result. Do not tune one lane and not the others. Use each CLI's default settings apart from what isolation needs, and list every non-default flag.
4. **A quiet, dedicated machine.** Record CPU model, core count, memory, OS, and the load average before each suite. Interleave lanes in every round (the suites already rotate the order). Report medians with the sample count, and min and max where the spread matters. Do not report a number from fewer than 10 samples as a result, except install size.
5. **Report losses.** The report must say where `nc` is slower, bigger, or heavier, with the same prominence as where it wins. Do not drop a metric because it is unflattering. If a lane fails a scenario, the table says "failed" and the text says why.
6. **Keep everything reproducible.** Raw JSONL stays in `results/<date>-<machine>/` and is committed. Every table in the report is generated by a script from that data.

## Measurements

Run each of these for all six lanes.

1. **Startup:** `<cli> --version`, 100 rounds, with `/usr/bin/true` as the floor. Wall time, CPU time, peak resident memory, and instructions retired where the platform gives them (`node harness/suite.mjs --parts=startup --rounds=100`).
2. **Time to first frame:** start the terminal interface in a PTY and time until its ready marker appears, 30 rounds (`--parts=firstframe`). Also record the time to the first byte.
3. **Idle cost:** the terminal interface left idle. CPU milliseconds per second and peak resident memory (`--parts=idle`). A healthy TUI uses about zero CPU while idle.
4. **One-shot:** one headless prompt with a one-word reply, 30 rounds. Spawn to request, total wall time, CPU, peak memory, bytes of the first request, and the number of side requests (`--parts=oneshot`).
5. **Streaming under load, headless:** the fixture streams 5 s of tokens at 100, 1,000 and 10,000 tokens per second (`node harness/sweep.mjs --mode=cli --rates=100,1000,10000 --samples=10`). Per-token lag p50 and p99 (server write to stdout), time from stream end to process exit, CPU for the run and per token, peak memory, and tokens that never reached stdout.
6. **Streaming under load, terminal interface:** the same streams typed into the TUI (`--mode=tui`). The capture is replayed through a VT emulator, so lag is measured by what is on screen. On-screen lag p50 and p99, stream end to last token on screen, Enter to request, CPU, peak memory, terminal bytes per token. Add 50,000 tokens per second if every lane survives 10,000.
7. **Install size:** disk used by what the install added (`BENCH_INSTALL_<LANE>`, `--parts=disk`), and separately whether the CLI needs a runtime (Node, Bun) that is not counted. Report the main binary's size too.
8. **Session store, if time allows:** 1,000 one-turn sessions per lane, then the size of the store on disk, the time to list sessions, and the time to continue the latest one. The 2026-10-28 harness did this for three lanes (`prior/` describes it); port it to `lanes.mjs` (`store` names each lane's directory).

## Known state (2026-11-09, macOS, not a clean machine)

- `nc`, `fx`: headless and terminal lanes pass the smoke.
- `claude` 2.1.316: headless passes with the environment in `lanes.mjs` and makes no side requests. Its terminal interface reaches the prompt after the config in `claudeSetup`. A streamed turn in it has not run, and an "Auto mode" notice may need dismissing.
- `codex` 0.162.0-alpha: `codex exec` passes. With `--json` it prints the reply at the end, so headless per-token lag is not meaningful for it. Find out whether any headless mode streams. Its terminal interface drew a frame and sent no request: look at the screen dump for a prompt it is waiting on.
- `opencode`: not installed or run. The config in `opencodeSetup` is a first guess.
- `pi`: ran on 2026-10-28 at 1.4.0. `pi -p` prints only at the end, so the lane uses `--mode json`.
- Linux: `tools/runstat.c` is macOS only. Without it the harness falls back to `tools/runstat.py`, which has no instruction counts or peak footprint. Add them with `perf stat` or cgroup `memory.peak` if the machine allows, and say which source each number has. `tui.py` and the fixture must read the same clock: check that lag is near zero for a lane you trust before believing any lag.
- A CLI that starts helper processes: `wait4` only counts children that were waited for. Check with `ps` whether a lane leaves helpers running, and if it does, measure the process group.

## Deliverables

1. `bench/cli/results/<date>-<machine>/`: raw JSONL, the machine description, versions, and the exact commands.
2. `bench/cli/results/<date>-<machine>/REPORT.md`, generated by `harness/report.mjs` (extend it): one table per measurement with all six lanes, then two short lists, "where nc leads" and "where nc trails", each item with its numbers.
3. A draft post, `bench/cli/results/<date>-<machine>/POST.md`, for nanocode.xyz/experiments. It explains the method in a paragraph, shows the tables, and explains the cause of the three largest differences (for example a runtime's startup, a renderer that redraws the whole screen, an event per token). State only what the data or a profile shows. Short paragraphs, no marketing words, every measurement dated.
4. A list of what could not be measured and why.

Stop and report instead of guessing if a CLI cannot be pointed at the fixture without an account.
