# nanocode vs fx vs pi — benchmark report (2026-10-29)

All numbers come from one Apple M1 Max (10 cores, 32 GB, macOS Darwin 25.3.0) against a local fake inference server in its own process. The machine was shared: load average 10–40 during the CLI, TUI, startup and session runs of 2026-10-29 (the SDK, stream-case, bridge and capacity tables are the 2026-10-28 runs at load 22–94; nothing on those paths changed), so medians are reliable to roughly ±20% and p99/max tails are inflated for every harness alike. Runs were interleaved/rotated between harnesses. The 2026-10-28 report is in results/archive-2026-10-28/REPORT.md.

## Targets

| lane | what ran |
|---|---|
| fx | release binary 0.0.15 (releases.fx.sh, macos-aarch64, 6.4 MB), pointed at the fixture with FX_GATEWAY_BASE_URL / FX_E2E_GATEWAY_* (the same overrides fx's own benchmarks use) |
| libfx-native / libfx-wasm | npm libfx 0.0.15 under Node 24.19.0 (wasm with --experimental-wasm-jspi), createFxEngine with the fx gateway protocol |
| pi / pi-json / pi-sdk | npm @earendil-works/pi-coding-agent 1.4.0 under Node 24.19.0 (pi -p, pi -p --mode json, createAgentSession), OpenAI Responses API |
| nc | nanocode CLI built from master 2c81984d0 (release profile; the 2026-10-28 run used 10776f335), Codex harness (gpt-6-luna) via --gateway vercel --gateway-base-url (HTTPS Responses) |
| nanocode-ts | gakonst/nanocode-ts 095cd57 (SDK daa1dbadc) WASM runtime in Node 24, Codex provider, live deltas, node:sqlite in memory |
| nanocode-native(-ws) | the Rust SDK in-process (output/hand-wiring sdkstream bin, Agent::builder + OpenAi), HTTPS and Responses WebSocket |

Every harness ran with an isolated HOME / agent dir in /tmp/bench-vs-ws (outside any repo, so no AGENTS.md). The fixture speaks the fx gateway stream, OpenAI Responses (SSE and WebSocket), Chat Completions and Anthropic Messages; tokens are `w<i> ` words with a paragraph break every 40, written on a timer at the requested rate (one SSE event / WS frame per token, batched per 1 ms tick). Lag = time the consumer saw token i minus the time the server wrote it, same monotonic clock across processes. TUI screens were replayed through a VT emulator (pyte) so differential renderers are measured by what is on screen.

## Headline

### Where nanocode leads
- Native SDK in-process (Rust): warm prompt to first text 0.69 ms over HTTPS and 0.38 ms over WebSocket, against 1.84 ms for pi and 2.46 ms for libfx-native in Node; per-token lag p99 at or under 1.2 ms at 1k–10k tok/s where the JS SDKs reach 104–180 ms.
- Headless one-shot: nc exec takes 20.5 ms wall (p50) against 43.6 ms for fx ask and 562 ms for pi -p.
- TUI: the first token reaches the screen 0.3–0.4 ms after the fixture writes it at every rate (pi 3–18 ms, fx 23 ms to 3.9 s because it prints a paragraph at a time), the last one 0.4–4.1 ms after the stream ends (fx 15–52, pi 4–210), keystroke echo is 0.23 ms p50 (fx 0.34, pi 0.53), and a 10k tok/s session uses 2.6 s of CPU against 3.4 s for fx.
- Headless streaming at low rates and in tails: at 10 tok/s nc uses less CPU than fx (16 against 18 ms for the run), and lag p99 at 10k tok/s is 0.11 ms against 0.15.
- Continuing the latest of 1,000 sessions and replying: 31 ms against 49.5 for fx and 558 for pi.
- Shell calls with heavy startup files: 7.7 ms per call p50 (fx 42.8 ms; pi 6.3 ms, but pi never loads startup files).
- Long tool turn (500 reads): 4.24 s at 36 MB RSS and 15 MB footprint; fx 9.41 s, pi 2.73 s at 428 MB.

### Where nanocode still trails
- Launch: nc --version takes 8.0 ms (6.3 min) against 3.7 for fx, at 33M instructions against 16M. What is left is the 47.7 MB image (69,957 dyld fixups against fx's 6,837) and clap building the whole command tree; the first TUI frame is 12.7 ms against 6.7.
- CPU per token at high rates: 22.6 µs at 10k tok/s against 16.1 for fx (1.4×), and 32.2 against 24.2 at 1k. A read loop alone costs 13–17 µs per network read blocking and 16–18 µs through Tokio and reqwest on this machine; the rest is the wakeups between hyper, the stream decoder, the event channel and the printer (ANALYSIS.md, follow-up).
- Session store: 18.8 MB for 1,000 one-turn sessions against 4.8 MB for fx and 8.0 for pi. What remains is about 2.9 KB of head rewrites and 7.2 KB of per-session records (environment context, checkpoint state, messages) per session, plus an index sidecar that may grow to twice its live size between rewrites. nc sessions takes 15.2 ms against 12.6.
- Long tool turn per step: 7.5 ms against 3.6 for pi. Almost all of it is creating a process for every exec_command (an external command costs 4–7 ms through the shell server, a builtin 1.2–1.5 ms); pi's read tool reads the file in-process, and the pinned Codex tool set has no such tool.
- Context weight: nc's first request is 61 KB (the pinned upstream Codex prompt plus the exec tool) against 25 KB for fx and 6 KB for pi.
- nanocode-ts (not changed in this round): warm first text 3.70 ms against pi 1.84, and 25 agents cost 563 ms and 133 MB because each instantiates its own WASM runtime.

### fx's own claims, checked here
- CLI dispatch is at the process floor: fx --version, help, status --json and sessions --json take 3.3–3.7 ms against 3.4 ms for /usr/bin/true. First interactive frame is 12 ms (p50), keystroke echo is 0.43 ms (p50), and exit takes 2 ms.
- libfx against pi on Node: pi wins warm first text at p50 (1.84 against 2.46 ms). fx's CI only reports the Node comparison and gates on Bun; Bun was not run here.
- libfx-wasm keeps a core busy while it waits: 902 ms of CPU over a 5 s stream at 10 tok/s, against 52 ms for the native addon. As its README states, it runs host tools one at a time: 8 calls of 50 ms take 419 ms, against 55 ms for native, pi and nanocode-ts.
- The fx TUI shows a reply one paragraph at a time. At 10 tok/s the first token appears 3.9 s after it arrives, which is the 40-token paragraph; at 100 tok/s it appears after 408 ms. Headless fx ask streams with no such delay.

### pi notes
- pi -p prints nothing until the reply is finished. pi -p --mode json streams, with 0.2–1 ms p50 lag but 14 MB of stdout for a 290 KB reply. Startup takes about 0.5 s and peak RSS is 150–435 MB.
- Side effect: one early pi 1.4.0 run (pi --version) was not yet isolated. It read the real ~/.pi/agent, installed the pi-autoresearch package listed there into ~/.pi/agent/npm, and rewrote ~/.pi/agent/models-store.json. Every later run used an isolated PI_CODING_AGENT_DIR and HOME.
